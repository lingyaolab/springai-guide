附录 F · 动手练习答案

这不是唯一答案，而是「参考实现 + 检查点」。同一道练习可以写出不同代码， 重点是你能不能解释每一步为什么这样做。建议先自己写，再对照。

怎么用这份答案

  • 先跑通自己的版本，再对照参考实现，不要直接抄。
  • 重点看「检查点」：它们比代码更能说明你有没有理解。
  • 如果代码能跑但检查点答不上来，回到对应章节重读。

第 01–02 章：环境与 ChatClient

01 的三个观察可以放在同一个工程里做：先固定温度，再删 key 看启动失败， 最后用依赖树确认 starter 的来源。 

spring:
  ai:
    deepseek:
      chat:
        temperature: 0
ChatResponse response = chatClient.prompt()
        .user("用一句话解释 RAG")
        .call()
        .chatResponse();

var usage = response.getMetadata().getUsage();
System.out.println(usage.getPromptTokens()
        + " + " + usage.getCompletionTokens()
        + " = " + usage.getTotalTokens());

检查点：

  • temperature=0 只是降低随机性，不保证三次逐字相同；厂商侧批处理与版本变化仍会影响结果。
  • 删掉 api-key 是启动时断言失败，不是请求时 401。先看启动日志第一段，不要先去查网络。
  • mvn dependency:tree 里应能追到 spring-ai-starter-model-deepseek → 自动装配模块 → spring-ai-deepseek。
  • 记忆隔离看的是 conversationId，不是 HTTP 会话；不同 id 互不可见，相同 id 才共享历史。

第 03–04 章：结构化输出与流式

嵌套 record 的 schema 会多一层 $defs / properties； 关键不是看 JSON 长什么样，而是看模型能否稳定填对嵌套字段。 

record Director(String name, int year) {}
record Movie(String title, Director director) {}

流式练习建议同时记录两个时间：首字时间与总耗时。只看总耗时，会误判首字体验。 

Disposable d = chatClient.prompt()
        .user("写一段 500 字的说明")
        .stream()
        .content()
        .doOnNext(System.out::print)
        .doOnCancel(() -> log.info("client cancelled"))
        .subscribe();

// 需要总时长上限时用 take；timeout 是空闲超时，不是总时长
// .take(Duration.ofSeconds(30))

检查点：

  • JSON 示例直接写进 user 提示词会和模板占位符冲突；修法是把示例作为参数传入，或按模板规则转义花括号。
  • validateSchema() 失败会触发重试；把 year 改成字符串后，应能看到重试日志而不是直接返回坏对象。
  • Flux.timeout 约束的是「多久没有下一个元素」，长回答一直有 chunk 就不会触发；总时长用 take(...)。
  • 关闭页面后，doOnCancel 应被调用；如果没有，检查响应式链路里是否有人把 Flux 转成了阻塞聚合。

第 05–06 章：记忆与 Advisor

窗口裁剪的最小实验：把上限调到 4，连续聊 5 轮，每轮打印 chatMemory.get(conversationId).size()。你会看到它稳定在 4 附近， 而不是无限增长。 

ChatMemory memory = MessageWindowChatMemory.builder()
        .chatMemoryRepository(repository)
        .maxMessages(4)
        .build();

// 新对话
memory.clear(conversationId);
public ChatClientRequest before(ChatClientRequest request, AdvisorChain chain) {
    request.context().put("requestId", UUID.randomUUID().toString());
    return request;
}

public ChatClientResponse after(ChatClientResponse response, AdvisorChain chain) {
    log.info("requestId={}", response.context().get("requestId"));
    return response;
}

检查点：

  • 裁剪发生在写入之后；保留条数按总消息数算，不是「保留几轮」。
  • clear(id) 只清该会话；用 userId + ":" + sessionId 时，两个 session 的 key 必须不同。
  • AuditAdvisor 的 order 改成 MIN + 350 后进入工具循环内侧，日志从「一次请求一条」变成「每轮循环一条」。
  • 缓存 Advisor 用 CallAdvisor，命中时直接返回构造好的 ChatClientResponse，不调用 chain.nextCall。
  • request.context() 是可变快照；ThreadLocal 在流式线程切换下不可靠。

第 07–08 章：RAG 与向量库

topK 的对比要同时记录三件事：回答是否正确、引用了几段、token 用了多少。 只看回答，容易把「多召回」误当成「更好」。 

var b = new FilterExpressionBuilder();

SearchRequest request = SearchRequest.builder()
        .query(question)
        .topK(4)
        .similarityThreshold(0.5)
        .filterExpression(b.eq("category", "refund").build())
        .build();

检查点：

  • topK=1 容易漏掉第二段答案；topK=10 可能把噪声和成本一起带进来。
  • 过滤表达式先缩小范围，再算相似度；不要把租户/分类过滤放到提示词里让模型自己判断。
  • 阈值调到 0.9 时「无法回答」变多，说明召回不足，不是模型变笨。
  • dimensions 必须与 embedding 输出一致；开启 schema-validation 后，错误会在启动/写入时更早暴露。
  • HNSW 与 NONE 的差异用 EXPLAIN ANALYZE 看执行计划，不要凭感觉判断索引有没有生效。

第 09–10 章：高级检索与工具

租户隔离的最小做法：每条文档写 tenant metadata，每次检索都强制拼上 tenant == 当前租户，而不是让模型决定查哪个租户。 

var b = new FilterExpressionBuilder();

var filter = b.and(
        b.eq("tenant", currentTenant),
        b.eq("status", "published")).build();

SearchRequest request = SearchRequest.builder()
        .query(question)
        .topK(4)
        .filterExpression(filter)
        .build();

检查点：

  • 「那运费呢？」单独检索几乎召回不到东西；改写后应包含「运费政策」这类可检索词。
  • numberOfQueries 从 3 调到 5 通常提高召回，也提高延迟与 token；默认多查询含原问题共 4 路。
  • 工具描述写成「查询数据」，模型就不知道何时调用；描述要写清输入、输出与适用场景。
  • throw-exception-on-error=false 时异常文本会回给模型；true 时直接中断调用。
  • ToolContext 里的 userId / tenantId 来自服务端，不进入工具参数 schema，模型无法篡改。

第 11–12 章：MCP 客户端与服务端

MCP 客户端的第一道边界不是提示词，而是工具过滤。只暴露读工具， 模型再聪明也不会调到删除接口。 

@Bean
McpToolFilter onlyReadOnlyTools() {
    return (connection, tool) -> !tool.name().startsWith("delete")
            && !tool.name().startsWith("write");
}
@McpTool(description = "按订单号查询订单状态，只读")
OrderView query(
        @McpToolParam(description = "订单号，例如 SO-20261106-001") String orderNo) {
    return this.orders.findViewByOrderNo(orderNo);
}

@McpResource(uri = "order://policy/refund", name = "退款政策")
String refundPolicy() {
    return Files.readString(Path.of("docs/refund-policy.md"));
}

检查点：

  • filesystem server 的挂载目录必须限制在测试目录；工具清单就是它能触达的文件面。
  • request-timeout=2s 只约束单次工具调用；慢工具的超时会以错误结果回到模型，不会拖垮整个进程。
  • Inspector 的 tools/list 验证「暴露了什么」，tools/call 验证「能不能执行」。
  • 加 Spring Security 后，不带 Bearer Token 应得到 401；不要把 MCP 端点当成内网就免鉴权。

第 13–14 章：观测、测试与生产化

测试的关键不是「调不调模型」，而是「断言什么」。捕获最后一次 Prompt， 比断言整段自然语言稳定得多。 

class CapturingChatModel extends StubChatModel {

    Prompt lastPrompt;

    CapturingChatModel(String reply) {
        super(reply);
    }

    @Override
    public ChatResponse call(Prompt prompt) {
        this.lastPrompt = prompt;
        return super.call(prompt);
    }
}

// 断言 RAG 拼进去的上下文
assertThat(model.lastPrompt.getContents())
        .contains("退款政策");
spring:
  ai:
    retry:
      max-attempts: 3          # 重试 3 次，总共最多 4 次请求
      backoff:
        initial-interval: 500ms
        multiplier: 2
        max-interval: 5s
      on-http-codes: [429]

检查点：

  • 工具测试要覆盖正常参数、缺参数、类型错误三种；异常应按框架规则转成可读结果。
  • Testcontainers 集成测试只验证「add → search」这条确定性链路，不调用真实模型。
  • max-attempts 是重试次数，不是总次数；3 次重试加首次共 4 次请求。
  • 429 默认不重试；加 on-http-codes: [429] 后要同时缩短退避，否则延迟会比失败更难接受。
  • Flux.timeout(10s) 是空闲超时；长回答持续有 chunk 时不会触发，总时长仍要靠 take(...)。

第 15–16 章：综合案例与评测

引用事件要在第一个 token 之前发出去。做法是先做一次检索，把文件名作为 citations 事件发出，再开始流式回答。 

List<String> citations = vectorStore.similaritySearch(
                SearchRequest.builder().query(question).topK(4).build())
        .stream()
        .map(doc -> doc.getMetadata().get("source").toString())
        .distinct()
        .toList();

emitter.send(SseEmitter.event().name("citations").data(citations));

chatClient.prompt()
        .user(question)
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
        .stream()
        .content()
        .subscribe(chunk -> send(emitter, "delta", chunk));

评测先算检索指标，再看生成指标。检索没召回，生成模型再强也只能编。 

recall@k = 命中的相关文档数 / 标注的相关文档总数
hit rate@k = 至少命中一条相关文档的问题数 / 问题总数

检查点：

  • 降级只在同步接口生效：流式一旦发出第一个 chunk，就不能无痕切换到另一个模型。
  • 引用要持久化到消息或事件里，不能只放在日志；前端刷新后还要能拿到。
  • 回归集四类样本：常规、同义改写、多轮追问、不该回答。
  • RelevancyEvaluator 只给通过/不通过，别把它当连续分数；换 judge 模型后通过率变化大，说明样本或提示词不稳。
  • CI 分层：单元与检索指标每次跑，真实 judge 与真实模型按需跑。

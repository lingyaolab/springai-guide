02 · ChatClient

ChatClient 是 Spring AI 对外的唯一主入口：你写的业务代码只跟它打交道， 模型厂商、HTTP 客户端、 Advisor、工具循环都在它背后。这一章把「一次对话」拆成请求规格、结果获取、流式、 运行时参数、多轮记忆五块，最后拼成一条完整调用链。

读完你能做到

  • 用三种方式拿到 ChatClient，并说清什么时候该用自动装配的 Builder
  • 写出带 system / user / 占位符的请求，并用 content、chatResponse、entity 三种方式取结果
  • 把同一个对话改成流式返回，并知道在 MVC 与 WebFlux 里分别该怎么写
  • 用 ChatMemory + MessageChatMemoryAdvisor 让第二轮对话记得第一轮

先说为什么：ChatModel 是发动机，ChatClient 是方向盘

ChatModel 只承诺一件事：给一个 Prompt，返回一个 ChatResponse。 它不负责模板、记忆、日志、工具循环，也不负责把结果转成你的 record。这些「横切关注点」全部在 ChatClient 这一层，靠 Advisor 链串起来。

你的代码：chatClient.prompt()...
只描述「这次要什么」，不关心厂商、不关心 HTTP。
ChatClient + Advisor 链
模板渲染、记忆读写、日志、安全过滤、检索增强、工具调用循环都挂在这里。2.0 起工具循环本身也是一个 Advisor。ToolCallingAdvisor.java:65
ChatModel（DeepSeekChatModel）
把 Prompt 翻成厂商请求，把响应翻回 ChatResponse。
DeepSeekApi / RestClient / WebClient
同步走 RestClient，流式走 WebClient。换模型只换这一层。
为什么本站后面只讲 ChatClient

因为 ChatClient 只依赖 ChatModel 接口。今天用 DeepSeek，明天换 Ollama、OpenAI、 通义，业务代码一行不用改。反过来，如果你直接调 DeepSeekChatModel 的厂商方法，就把自己焊死在 一个厂商上了。

最小可跑：三行拿到第一个回答

沿用 01 章的工程，只改 run() 方法：

@Override
public void run(String... args) {
    String answer = this.chatClient.prompt()
            .user("用一句话解释什么是向量数据库")
            .call()
            .content();
    System.out.println(answer);
}

这三行分别对应：

代码 返回值 你在这里决定什么
prompt() ChatClientRequestSpec 这次请求长什么样：系统提示、用户输入、参数、 Advisor
call() CallResponseSpec 同步执行，并选择要哪种结果形态
content() String 只要第一段文本，丢掉 token 用量等元数据

入口方法在 ChatClient.java:128， call() 与 stream() 在 ChatClient.java:490， content() 在 ChatClient.java:299。

逐行解读：容易懵的地方

写法 含义 常见误解
ChatClient.Builder 注入 自动装配给的 prototype Bean，每次注入都是新副本 以为它是单例，把它 build() 后当全局变量到处改配置
ChatClient.create(chatModel) 不经过 Spring 装配，直接包一个 ChatModel 在 Boot 工程里用它，会绕过所有自动配置的 Advisor
prompt() vs prompt("...") 前者自己拼 system/user，后者等价于 prompt().user(text) 以为 prompt("...") 会覆盖默认 system
content() 可能返回 null 方法签名是 @Nullable String 直接 .length() 触发 NPE
stream().content() 返回 Flux<String>，冷流，不订阅就不发请求 接住 Flux 却忘了返回给框架，控制台什么都不打印

请求规格：system / user / param 的四种写法

同一个请求有四种写法，按「变化频率」从高到低选：

// ① 最简单：只有用户输入
chatClient.prompt().user("你好").call().content();

// ② 字符串直给，等价于 ①
chatClient.prompt("你好").call().content();

// ③ system + user：角色约束写在 system 里
chatClient.prompt()
        .system("你是一个只回答 Java 问题的助教，回答不超过三句话。")
        .user("什么是虚拟线程？")
        .call()
        .content();

// ④ 模板 + 参数：同一段提示反复用时，把变量抽出来
chatClient.prompt()
        .system(s -> s.text("你是一个{role}，用{style}回答。")
                    .param("role", "数据库专家")
                    .param("style", "不超过 100 字"))
        .user(u -> u.text("解释一下 {topic}")
                    .param("topic", "MVCC"))
        .call()
        .content();

模板渲染由 TemplateRenderer 负责，默认用 {} 占位符；需要换成 <...> 时，在 Builder 上设置 defaultTemplateRenderer(...) ChatClient.java:525。 注意：如果 prompt 里出现 JSON 的 {，要么转义，要么换分隔符，否则会被当成占位符。

默认值放在 Builder 上，一次性设置

ChatClient.Builder 提供 defaultSystem()、defaultUser()、 defaultAdvisors()、defaultOptions()、defaultTools()。 它们的语义是「每次 prompt() 都先带上这些」，之后可以按次覆盖。 ChatClient.java:501

四种取结果的方式

只要文本

String s = client.prompt()
    .user(q)
    .call()
    .content();

最常用。拿不到文本时返回 null。

要元数据

ChatResponse r = client.prompt()
    .user(q)
    .call()
    .chatResponse();

能拿到 token 用量、finish reason、模型名。

record Movie(String title, int year, List<String> actors) {}

Movie movie = chatClient.prompt()
        .user("随便推荐一部 2000 年后的科幻电影")
        .call()
        .entity(Movie.class);

entity() 默认走「提示词约束 + JSON 解析」。模型返回的 JSON 不合法时会抛异常； 想要更稳，可以加两个开关：validateSchema() 校验失败自动带错误重试， useProviderStructuredOutput() 试图把 schema 直接交给厂商。但 2.0.2 的 DeepSeekChatOptions 没有实现 StructuredOutputChatOptions，所以在 DeepSeek 上打开它 会静默退回提示词方案——不报错，也没效果（第 03 章详述）。 

Movie movie = chatClient.prompt()
        .user("随便推荐一部 2000 年后的科幻电影")
        .call()
        .entity(Movie.class, spec -> spec
                .validateSchema()
                .useProviderStructuredOutput());

entity 的 4 个重载在 ChatClient.java:293； 两个开关的语义在 ChatClient.java:225。

流式：Flux 与 SSE

把 call() 换成 stream()，就能边生成边处理：

Flux<String> flux = chatClient.prompt()
        .user("写一段 200 字的产品介绍")
        .stream()
        .content();

// 逐块打印；blockLast 只是为了在命令行里演示
flux.doOnNext(System.out::print).blockLast();

stream() 返回的是冷流：只有被订阅时才真正发请求。在 Web 应用里，通常不要自己 subscribe，而是把 Flux 交给框架。

WebFlux：直接返回 Flux

@GetMapping(
  value = "/chat/stream",
  produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> stream(@RequestParam String q) {
    return chatClient.prompt()
        .user(q)
        .stream()
        .content();
}

MVC：用 SseEmitter 桥接

@GetMapping("/chat/stream")
public SseEmitter stream(@RequestParam String q) {
    SseEmitter emitter = new SseEmitter(0L);
    Disposable d = chatClient.prompt().user(q).stream().content()
        .subscribe(
            chunk -> {
                try { emitter.send(chunk); }
                catch (IOException e) { emitter.completeWithError(e); }
            },
            emitter::completeWithError,
            emitter::complete);
    emitter.onCompletion(d::dispose);
    emitter.onTimeout(d::dispose);
    return emitter;
}
流式的三个坑

① MVC 也能返回 Flux，但依赖 Reactor 与流式 produces，由 MVC 的 ReactiveTypeHandler 适配；同时引 web 与 webflux 时 Boot 默认仍选 Servlet 栈，行为容易和预期不一致。 要可控就用 SseEmitter，或只引 webflux 并显式设 web-application-type=reactive； ② 自己 subscribe() 后请求线程就结束了，必须把流交回容器或显式桥接到 SseEmitter； ③ 代理（Nginx）默认缓冲响应，需要在配置里关掉缓冲，否则用户仍然要等全部生成完。

StreamResponseSpec.content() 的签名是 Flux<String>ChatClient.java:382； 流式底层走 WebClientDeepSeekApi.java:177。

运行时参数与 DeepSeek 专属开关

全局参数写在 application.yml（01 章）；单次请求要覆盖时用 .options(...)。2.0 起 ChatOptions 是不可变对象，方法只接受 Builder： 

String answer = chatClient.prompt()
        .user("把这段合同条款压缩成 50 字")
        .options(DeepSeekChatOptions.builder()
                .temperature(0.1)
                .maxTokens(200)
                .build())
        .call()
        .content();

想开启思考模式（reasoning）时，DeepSeek 的属性里还有 thinking 与 reasoningEffort 两个开关；配置前缀同样是 spring.ai.deepseek.chat。 换模型时只需要把 DeepSeekChatOptions 换成对应厂商的 Options，ChatClient 代码不变。

Options 的 Builder 入口在 DeepSeekChatOptions.java:180； .options() 只收 ChatOptions.Builder 是 2.0 的编译期约束upgrade-notes.adoc:1478。

多轮记忆：ChatMemory + Advisor

01 章的 starter 已经顺带引入了 chat-memory 自动装配，所以容器里已经有一个 ChatMemory（内存版，窗口 20 条）： 

@Configuration
class ChatConfig {

    @Bean
    ChatClient chatClient(ChatClient.Builder builder, ChatMemory chatMemory) {
        return builder
                .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
                .build();
    }
}
@Service
class ChatService {

    private final ChatClient chatClient;
    ChatService(ChatClient chatClient) { this.chatClient = chatClient; }

    String chat(String userId, String question) {
        return this.chatClient.prompt()
                .user(question)
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, userId))
                .call()
                .content();
    }
}

关键点：会话 ID 必须每次调用时传。2.0 起内置记忆 Advisor 不再接受构造期默认会话 ID， 缺了会直接抛 IllegalArgumentException；ChatMemory.DEFAULT_CONVERSATION_ID 常量也已删除。

CONVERSATION_ID 的键名是 ChatMemory.java:36； 内存实现默认窗口 20 条MessageWindowChatMemory.java:45； 会话 ID 必填的变更说明upgrade-notes.adoc:1365。

内存版只适合单机演示

多副本部署时每个实例的对话历史互不可见。生产环境换 JDBC / Redis / MongoDB 仓库，第 05 章会讲三种存法的 表结构与配置差异。

端到端：一次 call() 到底走了哪些 Advisor

  • ① 渲染 Prompt
    把 system/user 模板与参数合成 Prompt，带上本次的 ChatOptions。
  • ② 进入 Advisor 链（order 越小越靠外）
    记忆 Advisor（MIN+200）最外层，先读历史；工具 Advisor（MIN+300）紧接着进入循环； 循环内部每一轮还会经过日志（0）、RAG（0）等 Advisor，最后到 ChatModel。 工具 Advisor 由自动装配注册。 ChatClientAutoConfiguration.java:100
  • ③ ChatModel 转协议
    DeepSeekChatModel 把消息、选项、工具定义翻成 DeepSeek 的请求体，交给 DeepSeekApi。
  • ④ 发 HTTP
    同步走 RestClient；流式走 WebClient 并逐块解析 SSE。
  • ⑤ 回来反向穿过 Advisor
    记忆 Advisor 把本轮问答写回 ChatMemory，日志 Advisor 记录耗时与 token，最后交给你。

    陷阱与窍门

    你会看到 NullPointerException 在 content() 之后

    因为content() 的签名是 @Nullable String，模型没有返回文本内容时 就是 null（例如只返回了工具调用）。改成先判空，或改用 chatResponse() 看 getResult().getOutput() 到底有什么。

    你会看到 IllegalArgumentException：缺少 conversation id

    因为2.0 起记忆 Advisor 强制要求每次调用提供 ChatMemory.CONVERSATION_ID。 改成在 .advisors(a -> a.param(...)) 里传，不要再用已删除的 .conversationId() 构造期写法。

    你会看到结构化输出偶尔解析失败

    因为entity() 默认靠提示词约束模型输出 JSON，模型可能加解释文字或漏字段。 改成先加 validateSchema() 让它自动重试；仍然不稳时，把 prompt 里的字段说明写全， 或改用更擅长结构化输出的模型。

    你会看到流式接口「一次性返回」

    因为返回值不是真正的流式通道：MVC 返回 Flux 会被聚合，或 Nginx 缓冲了响应。 改成MVC 用 SseEmitter，WebFlux 直接返回 Flux，并在反向代理关掉 proxy_buffering。

    温度不是「创造力开关」

    对合同抽取、分类、SQL 生成这类任务，先设 0–0.2；对文案、起名再设 0.7 以上。温度 0 也不保证完全确定性， 别把它当成可复现的保证。

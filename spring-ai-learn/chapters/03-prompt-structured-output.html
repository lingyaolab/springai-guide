03 · Prompt 模板与结构化输出

entity() 看起来只有一行，背后其实是「生成 JSON Schema → 把指令塞进用户消息 → 解析并清洗」三步。这一章把三步逐层拆开，并解释一个很少有人讲清楚的事实： useProviderStructuredOutput() 在 DeepSeek 上不会生效，而且不会报错。

读完你能做到

  • 写出带占位符的 system / user 模板，并知道默认分隔符是什么、怎么换
  • 说清 entity() 从 BeanOutputConverter 到最终对象的完整路径
  • 判断某个厂商是否支持「原生结构化输出」，以及不支持时框架会怎么退化
  • 用 validateSchema() 把「偶尔解析失败」变成「自动重试并给出原因」

先说为什么：模型只会输出字符串

大模型的响应本质是一段文本。你的程序要的是一个 Movie 对象、一个 List<Invoice>， 中间隔着「让模型按格式输出」和「把文本解析成对象」两件事。Spring AI 把这两件事收敛成一条路径：

① 生成 JSON Schema
从你的 Java 类型反射出结构（字段名、类型、是否必填）。 BeanOutputConverter.java:180
② 把「格式要求 + Schema」拼进提示词
作为 OUTPUT_FORMAT 放进请求上下文，最后追加到用户消息末尾。 ChatModelCallAdvisor.java:93
③ 清洗 + 反序列化
去掉思考标签、markdown 代码围栏、首尾空白，再交给 Jackson。 BeanOutputConverter.java:192
为什么默认方案是「提示词约束」而不是「厂商原生」

因为前者对所有模型都成立，后者要求厂商 API 支持 JSON Schema 参数。Spring AI 把两者做成 可切换的两条路，默认走前者，只有你显式打开开关且厂商实现了对应接口时，才走后者。

最小可跑：一个 record 就够

package com.example.demo;

import java.util.List;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
class MovieController {

    private final ChatClient chatClient;

    MovieController(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    // record 的字段名就是 JSON 的 key；嵌套类型会被递归展开成 schema
    record Movie(String title, int year, List<String> actors) {}

    @GetMapping("/movie")
    Movie recommend(@RequestParam(defaultValue = "科幻") String genre) {
        return this.chatClient.prompt()
                .user(u -> u.text("推荐一部{genre}电影，并给出片名、年份和三位主演。")
                            .param("genre", genre))
                .call()
                .entity(Movie.class);
    }
}

启动后访问 http://localhost:8080/movie?genre=科幻，返回的是真正的 JSON 对象，不是一段文本。 如果模型返回了 markdown 代码围栏，框架会在解析前清掉。

逐行解读：模板到底怎么渲染的

模板渲染发生在「请求规格 → Prompt」这一步，由 PromptTemplate 完成。默认渲染器是 StTemplateRenderer，分隔符是单个 { 和 }： 

private static final TemplateRenderer DEFAULT_TEMPLATE_RENDERER = StTemplateRenderer.builder().build();
private static final char DEFAULT_START_DELIMITER_TOKEN = '{';
private static final char DEFAULT_END_DELIMITER_TOKEN = '}';

默认渲染器PromptTemplate.java:51， 默认分隔符StTemplateRenderer.java:63。 system 与 user 各自独立渲染，只有传了 param 才会走模板替换 DefaultChatClientUtils.java:62 DefaultChatClientUtils.java:84。

最容易踩的坑：提示词里写了 JSON 示例

只要这段文本经过 {...} 渲染器，{"name": "x"} 里的 {"name"...} 就会被当成占位符；变量缺失时抛的是 IllegalStateException（ Not all variables were replaced in the template...）。两种解法：用反斜杠转义成 \{ / \}，或者换分隔符。 

ChatClient chatClient = ChatClient.builder(chatModel)
        .defaultTemplateRenderer(StTemplateRenderer.builder()
                .startDelimiterToken('<')
                .endDelimiterToken('>')
                .build())
        .build();

defaultTemplateRenderer 在 Builder 上ChatClient.java:525； 换成 < > 后 JSON 里的花括号就不再是特殊字符。

entity() 的完整调用链

把 02 章的一行代码展开，实际发生的是这五步：

  • ① 新建 Converter
    entity(Class<T>) 内部执行 new BeanOutputConverter<>(type)，构造时就把 JSON Schema 生成好了。DefaultChatClient.java:567
  • ② 把格式指令写进上下文
    OUTPUT_FORMAT 的值就是 converter.getFormat()，上下文 key 是 spring.ai.chat.client.output.format。 DefaultChatClient.java:598
  • ③ 调用模型时追加到用户消息
    ChatModelCallAdvisor 把格式指令拼在用户消息正文后面（不是 system）， 然后才调用 ChatModel。 ChatModelCallAdvisor.java:66
  • ④ 清洗响应文本
    默认清洗链是「去空白 → 去思考标签 → 去 markdown 代码围栏 → 再去空白」。 BeanOutputConverter.java:163
  • ⑤ Jackson 反序列化
    用 JsonMapper 转成目标类型；FAIL_ON_UNKNOWN_PROPERTIES 默认关闭，模型多返回字段不会炸。 BeanOutputConverter.java:204

    • 第 ③ 步拼出来的格式指令长这样（模板来自 BeanOutputConverter）：

    Your response should be in JSON format.
Do not include any explanations, only provide a RFC8259 compliant JSON response following this format without deviation.
Do not include markdown code blocks in your response.
Remove the ```json markdown from the output.
Here is the JSON Schema instance your output must adhere to:
```{"$schema":"https://json-schema.org/draft/2020-12/schema","type":"object", ...}```

    指令模板见 BeanOutputConverter.java:214； Schema 由 JsonSchemaGenerator.generateForType(type) 生成。

    原生结构化输出：为什么 DeepSeek 用不上

    entity(T.class, spec -> spec.useProviderStructuredOutput()) 的语义是「把 Schema 作为 API 参数发给厂商，让厂商在解码阶段保证 JSON」。它要生效，需要同时满足两个条件：

    1. 开关打开了，上下文里有 STRUCTURED_OUTPUT_NATIVE 且写入了 Schema；
    2. 本次请求的 ChatOptions 实现了 StructuredOutputChatOptions 接口—— ChatModelCallAdvisor 用 instanceof 判断，不满足就静默走回提示词方案。 
    if (usesNativeStructuredOutput && StringUtils.hasText(outputSchema)
        && chatRequest.prompt().getOptions() instanceof StructuredOutputChatOptions structuredOutputChatOptions) {
    var augmentedOptions = structuredOutputChatOptions.mutate().outputSchema(outputSchema).build();
    // ... 用原生 schema 调用
}
// 否则：把 outputFormat 追加到用户消息（提示词方案）

    关键事实：DeepSeekChatOptions 实现的是 ToolCallingChatOptions， 没有实现 StructuredOutputChatOptions。所以在 DeepSeek 上打开这个开关， 代码能编译、能运行、也不报错，但实际仍然走提示词约束。

    模型 Options 是否实现 StructuredOutputChatOptions
    OpenAI 是（OpenAiChatOptions.java）
    Anthropic 是
    Ollama 是
    Google GenAI / Mistral / Bedrock Converse 是
    DeepSeek 否，只会走提示词方案

    DeepSeekChatOptions 的声明DeepSeekChatOptions.java:44； 判定分支ChatModelCallAdvisor.java:81。

    所以在 DeepSeek 上该怎么写

    不要指望 useProviderStructuredOutput()，把力气花在提示词上：字段含义写清楚、给一个示例、 要求「只输出 JSON」。再加上下一节的 validateSchema()，稳定性比换开关高得多。

    validateSchema：失败自动重试的三层细节

    validateSchema() 会往 Advisor 链里压入一个 StructuredOutputValidationAdvisor，它在模型返回后做 JSON Schema 校验：

    细节 行为
    默认重试次数 maxRepeatAttempts = 3，加上首次一共最多 4 次请求
    校验标准 JSON Schema DRAFT 2020_12
    失败后怎么改 把「Output JSON validation failed because of: ...」追加到用户消息，重新调用
    Advisor 顺序 LOWEST_PRECEDENCE - 2000，位于工具循环内侧（order 越大越靠内），靠近 ChatModelCallAdvisor
    工具调用轮次 不校验（没有文本可校验），直接放行给工具 Advisor 
    Movie movie = chatClient.prompt()
        .user("推荐一部科幻电影")
        .call()
        .entity(Movie.class, spec -> spec.validateSchema());

    校验循环StructuredOutputValidationAdvisor.java:131， 默认重试次数StructuredOutputValidationAdvisor.java:247。

    重试是「再花一次钱」

    最坏情况下一次 entity() 会发 4 次请求、按 4 次计费。对高并发接口，建议只在关键字段上开校验， 或者把「格式要求」写得更死，减少第一次就失败的概率。

    不止 Bean：List / Map / 自定义 Converter

    需求 写法 底层
    单个对象 .entity(Movie.class) BeanOutputConverter
    泛型集合 .entity(new ParameterizedTypeReference<List<Movie>>() {}) BeanOutputConverter（保留泛型）
    只要字符串列表 .entity(new ListOutputConverter(conversionService)) 提示词要求逗号分隔，再切分
    任意 Map .entity(new MapOutputConverter()) 直接解析 JSON 对象
    特殊格式（CSV / XML） 自己实现 StructuredOutputConverter<T> 你控制 getFormat() 与 convert()

    自定义 Converter 的价值在于：getFormat() 决定提示词，convert() 决定解析。 框架只负责把 getFormat() 塞进请求，剩下的完全由你控制。这也是接自研协议时最干净的扩展点。

    速查表

    你要做的事 写法 / 默认值
    模板占位符 {name}，配合 .param("name", value)
    换分隔符 StTemplateRenderer.builder().startDelimiterToken('<').endDelimiterToken('>')
    取对象 .call().entity(X.class)
    取泛型集合 .entity(new ParameterizedTypeReference<List<X>>() {})
    要元数据 + 对象 .call().responseEntity(X.class)
    开启校验重试 spec -> spec.validateSchema()（最多 4 次请求）
    原生结构化输出 spec -> spec.useProviderStructuredOutput()（要求厂商支持）
    未知字段 默认忽略，不会抛异常

    陷阱与窍门

    模板里的 JSON 示例把请求搞崩了

    因为默认分隔符就是 { / }，JSON 的 { 被当成变量起点。 改成用反斜杠转义成 \{ / \}，或换 < > 分隔符。

    在 DeepSeek 上开了 useProviderStructuredOutput() 却没有任何变化

    因为DeepSeek 的 Options 没实现 StructuredOutputChatOptions，框架静默退回提示词方案。 改成删掉这个开关，改用 validateSchema() + 更明确的字段说明。

    字段名对不上，解析出来是 null 而不是报错

    因为默认关闭了 FAIL_ON_UNKNOWN_PROPERTIES，模型写错的 key 会被忽略。 改成用 @JsonProperty("snake_case_name") 显式对齐，或在 schema 描述里写清字段名。

    模型返回了 ```json 代码块

    因为有些模型习惯包一层 markdown。框架已处理：默认清洗链会去掉代码围栏。 但如果你自己 new ObjectMapper().readValue(...)，就要自己剥。

    让 schema 更「像人话」

    在 record 的字段上加注释不会进 schema 描述。想让模型理解字段含义，最有效的做法是在 getFormat() 之外再补一句自然语言说明，例如「year 是上映年份，不是故事发生年份」。

04 · 流式与 SSE

流式的难点不在 .stream() 这一行，而在它之后：每个元素到底是什么、 谁在什么线程上消费、用户关掉页面后请求会不会停、 出了错还能不能改 HTTP 状态码。这一章把这四件事讲透。

读完你能做到

  • 说清 stream().content() 每个元素是什么，以及它和 chatResponse() 的区别
  • 分别用 WebFlux 与 Spring MVC 写出真正逐字返回的接口
  • 解释「不订阅就不发请求」「用户断开后请求会取消」的原因
  • 在流式下正确处理记忆、观测、异常与超时，而不是等流结束才补救

先说为什么：同步是一次交付，流式是一串事件

.call() 的语义是「等全部生成完，一次性给我」。.stream() 的语义是 「模型每生成一小段就推给我一段」。后者带来三个新问题：连接要一直开着、消费速度可能跟不上生产速度、 中途失败时响应头已经发出去了。

ChatClient 层：Flux<ChatClientResponse>
每个元素是一小段增量响应，不是最终答案。
ChatModel 层：Flux<ChatResponse>
ChatModelStreamAdvisor 调 chatModel.stream(prompt)，并切到 boundedElastic 线程池。 ChatModelStreamAdvisor.java:53
HTTP 层：SSE
DeepSeek 用 WebClient.bodyToFlux(String.class) 接收 data: {...} 行，遇到 [DONE] 结束。 DeepSeekApi.java:182

最小可跑：命令行里逐字打印

Flux<String> flux = chatClient.prompt()
        .user("用 100 字介绍杭州")
        .stream()
        .content();

flux.doOnNext(System.out::print)   // 每来一小段就打印
    .blockLast();                   // 命令行里阻塞到结束

blockLast() 只适合命令行演示。在 Web 应用里不要自己 block，也不建议自己 subscribe——把 Flux 交给框架，由它管理连接与背压。

每个 chunk 到底是什么

StreamResponseSpec 只有三个方法，返回的都是 Flux：

方法 元素类型 用途
content() Flux<String> 只要文本增量；内部会过滤掉空串
chatResponse() Flux<ChatResponse> 要元数据、finish reason、tool call 增量
chatClientResponse() Flux<ChatClientResponse> 还要 Advisor 上下文 
return chatResponse()
        .map(r -> Optional.ofNullable(r.getResult())
                .map(Generation::getOutput)
                .map(AbstractMessage::getText)
                .orElse(""))
        .filter(StringUtils::hasLength);

三个方法的签名ChatClient.java:376； content() 的过滤逻辑DefaultChatClient.java:748。

每个元素不是「一个字」，而是一小段

模型按 token 生成，但网络传输与框架可能把多个 token 合在一个 chunk 里。不要假设「一个元素 = 一个汉字」， 也不要用「收到几次」去估算 token 数——用最后的 usage。

想要 token 用量，必须等流结束

大多数厂商把 usage 放在最后一个 chunk 里，甚至流式模式下不返回。需要精确计费时， 在流结束后用聚合后的 ChatResponse 取 getMetadata().getUsage()，或者回到 .call()。

接到浏览器：WebFlux 与 MVC 两种写法

WebFlux：直接返回 Flux

@GetMapping(
  value = "/chat/stream",
  produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> stream(@RequestParam String q) {
    return chatClient.prompt()
        .user(q)
        .stream()
        .content();
}

需要 spring-boot-starter-webflux。

MVC：用 SseEmitter 桥接

@GetMapping("/chat/stream")
public SseEmitter stream(@RequestParam String q) {
    SseEmitter emitter = new SseEmitter(0L); // 0 = 不超时
    Disposable d = chatClient.prompt()
        .user(q)
        .stream()
        .content()
        .subscribe(
            chunk -> {
                try { emitter.send(chunk); }
                catch (IOException e) { emitter.completeWithError(e); }
            },
            emitter::completeWithError,
            emitter::complete);
    emitter.onCompletion(d::dispose);
    emitter.onTimeout(d::dispose);
    return emitter;
}
SseEmitter 不设超时会继承容器默认值

Servlet 容器（如 Tomcat）的异步请求默认超时通常是 30 秒；SseEmitter 不显式设置时会继承它， 长回答容易被容器主动断掉。显式传 0L（不超时）或一个足够大的值， 并处理 onTimeout 释放上游订阅。Nginx 还要关掉 proxy_buffering，否则用户仍然 要等全部生成完才看到内容。

同时引了 web 和 webflux，为什么还是不流？

两个 starter 同时在 classpath 上时，Spring Boot 默认选 Servlet（MVC） 栈。MVC 虽然能适配 Flux，但要求 produces 是流式类型、且容器开启异步支持；这和「纯 WebFlux」的行为 不完全一致，排障时很容易误判。要么只引 webflux，要么设 spring.main.web-application-type=reactive。

订阅、取消与超时

Flux 是冷流：没有订阅者时，什么都不会发生。这一点在流式里尤其重要—— 你在 Controller 里只是「描述」了一条流，真正发请求是在框架订阅它的时候。

  • ① 订阅发生
    WebFlux 的响应式容器或 SseEmitter 的 subscribe 触发上游，WebClient 发 HTTP 请求。
  • ② 逐个 chunk 到达
    DeepSeek 的实现用 takeUntil("[DONE]") 决定何时结束，并过滤掉这个哨兵值。
  • ③ 取消传播
    客户端断网 / 关页面 → 容器取消订阅 → Flux 取消 → WebClient 关闭连接。很多厂商会因此 停止生成（是否停止取决于厂商实现），这正是「取消能省钱」的原因。
  • ④ 超时
    flux.timeout(Duration.ofSeconds(60)) 是空闲/间隔超时：每来一个 chunk 就重置， 既不是总时长，也不是首字节超时。总时长用 take(Duration) 或 takeUntilOther(Mono.delay(...))；首字节用 timeout(Mono.delay(...)) 这个接收 Publisher 的重载，或把连接超时设在 HTTP 客户端上。 
    • Flux<String> flux = chatClient.prompt()
        .user(q)
        .stream()
        .content()
        .take(Duration.ofSeconds(90))
        .doOnCancel(() -> log.info("客户端断开，生成已取消"))
        .doOnComplete(() -> log.info("生成完成"));

    结束条件与哨兵过滤DeepSeekApi.java:184； 终端 Advisor 的线程切换ChatModelStreamAdvisor.java:58。

    流式下的记忆与观测：框架在背后做了聚合

    流式会产出几十上百个 chunk，但记忆里不会出现几十条 assistant 消息。原因在 MessageChatMemoryAdvisor 的流式实现：它把整条流聚合完，再调用一次 after()。 

    return Mono.just(chatClientRequest)
        .publishOn(scheduler)
        .map(request -> this.before(request, streamAdvisorChain))
        .flatMapMany(streamAdvisorChain::nextStream)
        .transform(flux -> new ChatClientMessageAggregator()
                .aggregateChatClientResponse(flux, response -> this.after(response, streamAdvisorChain)));

    观测也是同理：DefaultStreamResponseSpec 一边把 chunk 发给你，一边用 ChatClientMessageAggregator 聚合出完整响应写入 observation。所以你在追踪系统里看到的是 一次完整调用，不是 N 次。

    记忆的聚合写回MessageChatMemoryAdvisor.java:161； 观测聚合DefaultChatClient.java:731。

    聚合的代价

    ChatClientMessageAggregator 需要在内存里保留整段文本直到流结束。超长回答（几万字）时， 这是一份额外的内存占用；同时它意味着记忆写入发生在流结束之后，中途取消则这一轮不会进记忆。

    错误处理：响应头发出去之后就晚了

    流式错误分两个阶段，处理方式完全不同：

    阶段 还能改 HTTP 状态码吗 做法
    首个 chunk 之前 能 异常正常冒泡，全局异常处理器返回 4xx/5xx
    首个 chunk 之后 不能，响应头已提交 发一个错误事件，或补一句兜底文本，然后正常结束 
    Flux<String> flux = chatClient.prompt()
        .user(q)
        .stream()
        .content()
        .onErrorResume(ex -> Flux.just("\n[生成中断：" + ex.getMessage() + "]"));
    不要在前端只判断 HTTP 200

    流式接口即使中途失败，HTTP 状态往往已经是 200。前端必须监听 SSE 的 error 事件或自定义的结束标记，否则会把「半截回答」当成成功。

    背压与首字延迟

    Reactor 的背压会让上游按下游的请求量生产，但中间经过 publishOn(boundedElastic) 后， 会有一个预取队列（默认 256 个元素）。对文本流来说这通常无所谓，但如果你在 doOnNext 里做 落库、调外部接口这类阻塞操作，就会拖慢整个流，并把线程占在 boundedElastic 上。

    该做的

    • 在 doOnNext 里只做轻量转换或推送
    • 落库、审计放到流结束后统一处理
    • 用 timeout 限制总时长，避免连接悬挂

    不该做的

    • 在流里 block() 或 sleep()
    • 用 flatMap 并发处理 chunk，打乱顺序
    • 把整段文本拼在内存里再一次性返回（那就失去流式的意义）

    「首字延迟」主要由模型与网络决定，代码能做的只有：选更快的模型、别在调用前做重活、把 maxTokens 设合理、避免在 Advisor 链里加阻塞逻辑。

    你要做的事 写法

    命令行演示 .blockLast()（仅限非 Web 场景）

    陷阱与窍门

    接了 Flux 但什么都不输出

    因为冷流没有被订阅。改成把 Flux 返回给 WebFlux 容器，或在 MVC 里 subscribe 到 SseEmitter。

    接口「流式」但用户要等全部生成完

    因为返回值没有真正走进流式通道：MVC 下 produces 或异步适配不对，或 Nginx 开了 proxy_buffering，或中间还有一层网关在缓冲。改成按栈选正确的写法，并逐层关缓冲。

    长回答总是 30 秒断掉

    因为SseEmitter 没设超时，继承了容器默认的异步超时（Tomcat 常见 30 秒）。 改成构造时传 0L 或显式设置足够大的超时，并在超时回调里取消上游。

    记忆里出现了半截回答

    因为你在自定义 Advisor 里逐 chunk 写库，或者流被取消时触发了自己的回调。 框架的默认记忆 Advisor 是聚合后才写一次；自定义逻辑不要破坏这个语义。

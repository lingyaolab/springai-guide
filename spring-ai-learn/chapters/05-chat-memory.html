05 · 多轮记忆

「让模型记住上一轮」听起来像加个参数，实际要回答三个问题：存什么、存哪、 什么时候塞回上下文。Spring AI 把这三件事拆成 ChatMemory（策略）、 ChatMemoryRepository（存储）、MessageChatMemoryAdvisor（时机）三层。 这一章把三层逐个拆开。

读完你能做到

  • 说清 ChatMemory 与 ChatMemoryRepository 各自负责什么，为什么不能合成一个接口
  • 解释 MessageWindowChatMemory 的裁剪算法：为什么它总是从一条 user 消息开始保留
  • 用 MessageChatMemoryAdvisor + conversationId 跑通两轮对话，并知道消息在什么时候被写入
  • 在内存 / JDBC / Redis 三种存储之间做选择，并写对 2.0.2 的配置前缀

先说为什么：记忆是「策略 + 存储」两件事

如果只有一个 ChatMemory 接口，你会被迫在「怎么裁剪」和「存到哪」之间二选一： 换数据库要重写裁剪逻辑，改窗口大小又要动存储代码。Spring AI 把它拆成两半：

ChatMemory（策略：留多少、怎么拼）
唯一的内置实现是 MessageWindowChatMemory：决定窗口大小、系统消息怎么保留、超限先删谁。 MessageWindowChatMemory.java:43
ChatMemoryRepository（存储：读写消息列表）
只有四个方法：列出会话、按会话读、按会话整段覆盖写、按会话删。 ChatMemoryRepository.java:29
MessageChatMemoryAdvisor（时机：读历史 / 写新消息）
在调用模型前把历史拼进 prompt，在返回后把 assistant 消息写回记忆。 MessageChatMemoryAdvisor.java:74
为什么要拆成「策略 + 存储」

因为两者变化频率不同：窗口大小是产品决策（20 条还是 50 条），存储是部署决策（单机内存还是 Redis）。 拆开之后，换 Redis 不需要改裁剪逻辑，改窗口也不需要动存储实现。

最小可跑：两轮对话记住名字

01 章的 starter 已经带来了 ChatMemory 自动装配，只需要把 Advisor 挂上：

package com.example.demo;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.client.advisor.MessageChatMemoryAdvisor;
import org.springframework.ai.chat.memory.ChatMemory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ChatConfig {

    @Bean
    ChatClient chatClient(ChatClient.Builder builder, ChatMemory chatMemory) {
        return builder
                .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
                .build();
    }
}
package com.example.demo;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.memory.ChatMemory;
import org.springframework.stereotype.Service;

@Service
class ChatService {

    private final ChatClient chatClient;

    ChatService(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    String chat(String conversationId, String question) {
        return this.chatClient.prompt()
                .user(question)
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
                .call()
                .content();
    }
}
String id = "user-42";
System.out.println(service.chat(id, "我叫小林，记住这个名字"));
System.out.println(service.chat(id, "我刚才说我叫什么？"));

System.out.println(service.chat("user-99", "我刚才说我叫什么？")); // 另一个会话，应该不知道

同一个 conversationId 共享一份历史，不同的 ID 完全隔离。会话 ID 由你决定怎么拼—— 常见的是 userId + ":" + sessionId，这样同一个用户可以有多个互不干扰的对话。

窗口算法：20 条上限背后有三个细节

MessageWindowChatMemory 默认最多保留 20 条消息。但它的裁剪不是简单的「从头删」， 而是有三条明确规则：

  • ① 新的 SystemMessage 会顶掉旧的
    如果本次新增的消息里包含 SystemMessage，旧的 SystemMessage 会先被清掉，避免多条互相矛盾的 system 指令 同时存在。MessageWindowChatMemory.java:89
  • ② 系统消息永远不参与淘汰
    计算要删多少条时，只统计非 system 消息；即使窗口满了，system 消息也会保留。 MessageWindowChatMemory.java:101
  • ③ 裁剪点会向后对齐到一条 user 消息
    按数量算出的切点如果落在 assistant 或 tool 消息上，会继续往后找，直到遇到 user 消息。 这样保留下来的窗口总是从「完整的一轮」开始，不会出现「有回答却没有提问」的上下文。 MessageWindowChatMemory.java:116
    • 这条对齐规则为什么重要

    如果没有它，窗口边界可能切在「assistant 回答」后面，模型看到的第一条消息是一句没有上下文的回答， 容易顺着错误的方向续写。对齐到 user 消息，等于强制「按轮」保留。 

    @Bean
ChatMemory chatMemory(ChatMemoryRepository repository) {
    return MessageWindowChatMemory.builder()
            .chatMemoryRepository(repository)
            .maxMessages(10)   // 必须 > 0
            .build();
}

    默认窗口 20MessageWindowChatMemory.java:45； maxMessages 必须大于 0，否则构造时断言失败MessageWindowChatMemory.java:53。

    Advisor 到底在前后做了什么

    MessageChatMemoryAdvisor 的默认 order 是 HIGHEST_PRECEDENCE + 200， 比工具 Advisor 更靠外，所以它看到的是「工具循环已经结束」的最终消息。

    before：拼历史 + 立刻写 user 消息

    • 按 conversationId 读出历史
    • 如果 prompt 里已经包含这段历史（例如你手动传了 .messages(...)），不再重复插入
    • 把 SystemMessage 移到最前面
    • 把本轮 user 消息先写进记忆，然后才调用模型

    after：写 assistant 消息

    • 取本次响应的所有 generation
    • 作为 assistant 消息写回同一个 conversationId
    • 返回原始响应，不改内容
    // before
List<Message> memoryMessages = this.chatMemory.get(conversationId);
// ...拼成 processedMessages，system 置顶...
Message userMessage = processedChatClientRequest.prompt().getLastUserOrToolResponseMessage();
this.chatMemory.add(conversationId, userMessage);   // 先写 user

// after
this.chatMemory.add(this.getConversationId(response.context()), assistantMessages);

    默认 orderAdvisor.java:39； before 与去重MessageChatMemoryAdvisor.java:78； after 写回MessageChatMemoryAdvisor.java:137。

    这个顺序带来一个副作用

    user 消息在调用模型之前就已经写进记忆。如果这次模型调用失败（超时、限流、401）， 记忆里会留下一条没有回答的提问；客户端重试时会再写一条，形成重复。生产环境要在重试前用 clear() 或自己做幂等，别让失败请求污染上下文。

    存储选型：内存 / JDBC / Redis

    实现 引入方式 适合 要注意
    InMemoryChatMemoryRepository spring-ai-starter-model-chat-memory（DeepSeek starter 已带） 单机演示、单元测试 重启即丢；多副本之间不共享
    JdbcChatMemoryRepository spring-ai-starter-model-chat-memory-repository-jdbc 已有关系库、要能用 SQL 查 每次写入是整段覆盖；表要按方言建
    Redis 仓库 spring-ai-starter-model-chat-memory-repository-redis 多副本、低延迟、要 TTL 2.0.1 改过 artifact 与配置前缀
    Mongo / Cassandra / Neo4j ...-repository-mongodb 等 已有对应基础设施 各自有额外的索引/表初始化

    无论换哪种存储，ChatMemory 这一层都不用改：MessageWindowChatMemory.builder() .chatMemoryRepository(newRepo) 就够了。这正是前面「策略 + 存储」拆分的收益。

    JDBC：表结构、sequence_id 与初始化开关

    JDBC 仓库的核心表只有一张。下面是测试用的 HSQLDB 脚本；PostgreSQL / MySQL 的列类型由各自方言决定，字段名不变：

    CREATE TABLE IF NOT EXISTS SPRING_AI_CHAT_MEMORY (
    conversation_id VARCHAR(36) NOT NULL,
    content         LONGVARCHAR NOT NULL,
    type            VARCHAR(10) NOT NULL,
    timestamp       TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    sequence_id     BIGINT NOT NULL
);

    sequence_id 是 2.0.0 新加的列，用来决定同一会话内的消息顺序；只靠 timestamp 在同一毫秒写入多条时会乱序。升级已有库时必须补这一列。

    表结构schema.sql:2； sequence_id 的引入说明chat-memory.adoc:210。

    配置项 默认值 说明
    spring.ai.chat.memory.repository.jdbc.initialize-schema embedded embedded / always / never
    spring.ai.chat.memory.repository.jdbc.schema classpath:.../schema-@@platform@@.sql 自定义建表脚本位置
    spring.ai.chat.memory.repository.jdbc.platform 自动探测 脚本里的 @@platform@@ 占位符

    配置项与默认值见 chat-memory.adoc:201。

    生产库不要用 always 去「自动建表」

    默认的 embedded 只对内嵌库建表，生产环境通常设为 never，把建表交给 Flyway / Liquibase。否则应用启动时可能因为权限不足或并发建表失败，把整个服务卡在启动阶段。

    Redis：前缀在 2.0.1 改过名

    2.0.1 把这个模块的 artifact 和配置前缀一起改了：artifact 加上 -repository-， 属性前缀从 spring.ai.chat.memory.redis.* 变为 spring.ai.chat.memory.repository.redis.*。旧属性还留了兼容，但已标记弃用。

    配置项（新前缀） 默认值 说明
    ...repository.redis.host / port localhost / 6379 连接信息
    ...repository.redis.index-name chat-memory-idx Redis Search 索引名
    ...repository.redis.key-prefix chat-memory: key 前缀，多环境共用实例时务必改
    ...repository.redis.time-to-live 不设置（不过期） 例如 24h；会话数据不该永久堆积
    ...repository.redis.initialize-schema true 是否在启动时建索引

    改动说明upgrade-notes.adoc:54； 配置项与默认值chat-memory.adoc:556。

    端到端：一次多轮请求的时间线

  • ① 进入 Advisor 链
    记忆 Advisor 的 order 很小，先于工具与日志 Advisor 执行。
  • ② 读历史
    chatMemory.get(conversationId) → 仓库按会话查出消息列表。
  • ③ 拼 prompt 并写 user
    历史 + 本轮消息合并，system 置顶；本轮 user 消息立即写回记忆。
  • ④ 调模型
    后续 Advisor 与 ChatModel 看到的已经是带历史的完整 prompt。
  • ⑤ 写 assistant
    响应回来后 chatMemory.add(conversationId, assistantMessages)，窗口裁剪在这一步发生。
  • ⑥ 落库
    saveAll 用整段消息覆盖该会话——所以窗口上限同时也是单次写入的上限。

    • 速查表

    你要做的事 写法
    挂记忆 Advisor .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
    指定会话 .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, id))
    改窗口大小 MessageWindowChatMemory.builder().maxMessages(n)
    换存储 .chatMemoryRepository(repo)
    清空某会话 chatMemory.clear(conversationId)
    列出所有会话 chatMemoryRepository.findConversationIds()
    调整 Advisor 顺序 MessageChatMemoryAdvisor.builder(m).order(n).build()

    陷阱与窍门

    启动正常，第一次调用抛 IllegalArgumentException: conversationId cannot be null

    因为2.0 起记忆 Advisor 强制要求会话 ID，取不到就断言失败。 改成每次调用都传 ChatMemory.CONVERSATION_ID。 BaseChatMemoryAdvisor.java:41

    抄了 .conversationId("default") 编译不过

    因为2.0 删掉了 Builder 上的 conversationId()，也删掉了 ChatMemory.DEFAULT_CONVERSATION_ID。改成把会话 ID 放到调用上下文里传。

    本地测得好好的，上线后每个副本各记各的

    因为用了内存仓库。改成换 JDBC / Redis，并把会话 ID 设计成与实例无关 （不要拼进程 ID 或随机数）。

    聊到第 30 轮，模型忘了你最开始定的规则

    因为窗口只保留 20 条，早期消息被裁掉了。改成把长期约束写进 SystemMessage ——系统消息不参与淘汰；或者把关键事实沉淀到外部存储，每轮检索后再注入。

    会话 ID 的命名值得单独设计

    userId 一个人一个会话，会让「同一用户开两个话题」互相污染。推荐 userId + ":" + sessionId，并在前端明确「新建对话」的动作，对应一个新的 sessionId。

    自检三问

    1. 为什么裁剪点要对齐到 user 消息，而不是直接按数量切？
    2. 模型调用失败时，记忆里会不会留下这轮提问？为什么？
    3. 把存储从内存换成 JDBC，需要改动 ChatMemory 的哪一部分？

    20 分钟动手练习

    1. 把 maxMessages 改成 4，连续聊 5 轮，打印每轮 chatMemory.get(id).size()，观察裁剪时机。
    2. 给 session 加一个「新对话」接口，调用 chatMemory.clear(id)，验证清空后模型不再记得。
    3. 把会话 ID 改成 userId + ":" + sessionId，验证同一用户的两个 session 互不干扰。

06 · Advisor 机制

Advisor 是 Spring AI 的中间件：日志、记忆、RAG、工具循环、结构化输出校验，全都是 Advisor。 理解它只需要抓住三件事：order 决定谁在外面、before/after 决定你能改哪一段、 流式下 after 只触发一次。这一章把这三件事讲透，然后手写一个。

读完你能做到

  • 看懂 order 数值与「内层/外层」的对应关系，能推出记忆、工具、RAG 的相对位置
  • 用 BaseAdvisor 写一个审计 Advisor，并解释流式下 after 为什么只跑一次
  • 知道什么时候必须直接实现 CallAdvisor（短路），而不能用 BaseAdvisor
  • 说清工具循环为什么能「递归」穿过同一条链，以及如何避免重复注册

先说为什么：横切逻辑不该散落在业务里

没有 Advisor，你会在每个 chatClient.prompt() 前后手写：读记忆、拼 RAG、记日志、算耗时、 校验 JSON、执行工具。这些逻辑和「问什么问题」无关，却要重复几十遍。Advisor 把它们抽成一层， 由框架按顺序套在模型调用外面。

外层 Advisor（order 小）
先执行 before，最后执行 after。适合做记忆、审计、全局兜底。
内层 Advisor（order 大）
后执行 before，先执行 after。适合做与单次模型调用强相关的逻辑。
终点：ChatModelCallAdvisor / ChatModelStreamAdvisor
order 是 LOWEST_PRECEDENCE，负责真正调用模型。 ChatModelStreamAdvisor.java:68

最小可跑：给 ChatClient 加一个日志 Advisor

先把一个 Advisor 跑起来，再研究它排在哪。Spring AI 自带 SimpleLoggerAdvisor，不需要写代码： 

ChatClient chatClient = ChatClient.builder(chatModel)
        .defaultAdvisors(new SimpleLoggerAdvisor())
        .build();

String answer = chatClient.prompt()
        .user("用一句话解释 Advisor")
        .call()
        .content();

默认日志级别是 DEBUG，所以要打开 logging.level.org.springframework.ai.chat.client.advisor.SimpleLoggerAdvisor=DEBUG 才能看到请求与响应。看到日志后，再改一个参数观察顺序： 

new SimpleLoggerAdvisor(Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER + 50)

把它放到记忆之后、工具之前，日志就从「每次模型调用一条」变成「整轮对话一条」。 这就是下一节 order 要解释的事。

默认 order 与两个构造器SimpleLoggerAdvisor.java:57； DEBUG 门控SimpleLoggerAdvisor.java:93。

order：数值越小越靠外

Advisor 继承 Ordered，链在构建时用 OrderComparator.sort 升序排列。 所以「order 越小」= 越早进入 before、越晚执行 after，也就是越外层。

Advisor order 位置
MessageChatMemoryAdvisor MIN_VALUE + 200 最外层：记忆包住整个工具循环
ToolCallingAdvisor MIN_VALUE + 300 记忆内层：它自己管中间的工具消息
SimpleLoggerAdvisor / QuestionAnswerAdvisor / SafeGuardAdvisor 0 工具循环内部：每轮循环都会经过
StructuredOutputValidationAdvisor MAX_VALUE - 2000 靠近终点：只包住模型调用，便于重试
ChatModelCallAdvisor / ChatModelStreamAdvisor MAX_VALUE 终点

记忆与工具的常量Advisor.java:39、 ToolCallingAdvisor.java:75； 排序发生在链构建时DefaultAroundAdvisorChain.java:277。

一个容易反直觉的推论

因为 SimpleLoggerAdvisor 与 QuestionAnswerAdvisor 的 order 都是 0，它们位于工具 Advisor 内侧。一次带工具的对话里，日志会记录每一轮模型调用，RAG 也会在每一轮重新检索。 这不是 bug，而是 order 的直接结果。

order 相同的 Advisor，执行顺序不保证（官方明确说 unspecified）。当前实现会先 addFirst 再稳定排序，实际顺序与注册顺序相反。所以不要依赖「都是 0 时谁先谁后」这种巧合—— 需要确定的顺序就显式给不同的值。advisors.adoc:79

BaseAdvisor：before / after 的默认骨架

大多数自定义 Advisor 只需要实现 BaseAdvisor，它把同步与流式的骨架都写好了，你只填两个方法： 

ChatClientRequest processed = before(request, chain);
ChatClientResponse response = chain.nextCall(processed);
return after(response, chain);

流式实现多了一步 publishOn(scheduler)（默认 boundedElastic），并且 只有当某个 chunk 带有 finish reason 时才调用 after： 

chatClientResponseFlux.map(response -> {
    if (AdvisorUtils.onFinishReason().test(response)) {
        response = after(response, streamAdvisorChain);
    }
    return response;
})

adviseStream 的默认骨架BaseAdvisor.java:57； finish reason 判定AdvisorUtils.java:40。

流式下 after 的三个「不会」

不会每个 chunk 都执行；流被取消时不会执行；流以错误结束时不会执行（错误路径走 onErrorResume 重新抛）。所以「在 after 里计费/写审计」在流式场景可能漏记，关键逻辑要同时覆盖 doOnCancel / doOnError。

短路：为什么 SafeGuard 不用 BaseAdvisor

BaseAdvisor 的 before 只能改请求，不能「不调用模型直接返回」。 想拦截请求并直接给出响应，必须自己实现 CallAdvisor / StreamAdvisor，选择不调用 nextCall： 

public ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain) {
    if (containsSensitiveWord(request)) {
        return createFailureResponse(request);   // 不调 chain，模型根本不会被调用
    }
    return chain.nextCall(request);
}

短路实现SafeGuardAdvisor.java:83； 它同时实现了 CallAdvisor 与 StreamAdvisor，流式下返回一个单元素 Flux。

「改请求」用 BaseAdvisor，「换结果」用 CallAdvisor

想在用户问题前面加一句系统提示、改参数、加 metadata → BaseAdvisor.before。 想命中敏感词就返回固定话术、想走缓存命中直接返回 → 直接实现 CallAdvisor。

手写一个：审计 Advisor

需求：记录每次调用的用户问题、耗时与 token 用量，放在记忆之后、工具之前（这样一次对话只记一条， 而不是每轮循环记一条）。 

package com.example.demo;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.ai.chat.client.ChatClientRequest;
import org.springframework.ai.chat.client.ChatClientResponse;
import org.springframework.ai.chat.client.advisor.api.Advisor;
import org.springframework.ai.chat.client.advisor.api.AdvisorChain;
import org.springframework.ai.chat.client.advisor.api.BaseAdvisor;
import org.springframework.ai.chat.model.ChatResponse;

public class AuditAdvisor implements BaseAdvisor {

    private static final Logger log = LoggerFactory.getLogger(AuditAdvisor.class);

    private final ThreadLocal<Long> startedAt = new ThreadLocal<>();

    @Override
    public ChatClientRequest before(ChatClientRequest request, AdvisorChain chain) {
        this.startedAt.set(System.currentTimeMillis());
        log.info("question: {}", request.prompt().getLastUserOrToolResponseMessage().getText());
        return request;
    }

    @Override
    public ChatClientResponse after(ChatClientResponse response, AdvisorChain chain) {
        long cost = System.currentTimeMillis() - this.startedAt.get();
        ChatResponse chatResponse = response.chatResponse();
        if (chatResponse != null) {
            var usage = chatResponse.getMetadata().getUsage();
            log.info("cost={}ms, tokens={}", cost, usage.getTotalTokens());
        }
        return response;
    }

    @Override
    public int getOrder() {
        // 记忆（+200）之后、工具（+300）之前
        return Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER + 50;
    }
}
ChatClient chatClient = ChatClient.builder(chatModel)
        .defaultAdvisors(
                MessageChatMemoryAdvisor.builder(chatMemory).build(),
                new AuditAdvisor())
        .build();
ThreadLocal 在流式下不可靠

流式的 before 与 after 可能跑在 boundedElastic 的不同线程上。 示例为了简洁用了 ThreadLocal，生产代码应该把开始时间放进 request.context()（一个可变的 Map 快照，沿链共享），或直接用 Observation / Micrometer。

注册方式与 per-call 参数

方式 作用范围 写法
defaultAdvisors(...) 该客户端的所有请求 ChatClient.builder(m).defaultAdvisors(a1, a2).build()
advisors(...) 仅本次请求，追加到默认之后 .advisors(new XxxAdvisor())
advisors(Consumer<AdvisorSpec>) 既可加 Advisor（a.advisors(...)），也可设置参数 .advisors(a -> a.param("k", v))

Advisor 是普通对象，不会因为声明成 @Component 就自动进入链——必须显式注册。 请求级参数通过 request.context() 传递，Advisor 用常量 key 读取（记忆 Advisor 读 ChatMemory.CONVERSATION_ID、RAG 读 QuestionAnswerAdvisor.FILTER_EXPRESSION）。

框架还提供两个预设参数：AdvisorParams.ENABLE_NATIVE_STRUCTURED_OUTPUT 与 AdvisorParams.toolCallingAdvisorAutoRegister(false)。后者用于「我想自己注册工具 Advisor」的场景。

内置 Advisor 一览

Advisor 作用 默认 order
MessageChatMemoryAdvisor 读写会话历史 MIN + 200
ToolCallingAdvisor 工具循环（2.0 自动注册） MIN + 300
SimpleLoggerAdvisor 打印请求与响应 0
SafeGuardAdvisor 敏感词拦截，直接返回固定话术 0
QuestionAnswerAdvisor RAG 检索并拼上下文 0
StructuredOutputValidationAdvisor JSON Schema 校验 + 重试 MAX - 2000

递归：工具循环如何穿过同一条链

ToolCallingAdvisor 执行完工具后，需要再问一次模型。它不是直接调 ChatModel， 而是调用 callAdvisorChain.copy(this).nextCall(...)——拿到「排在自己后面」的那段链重新走一遍。 

public CallAdvisorChain copy(CallAdvisor after) {
    return this.copyAdvisorsAfter(this.getCallAdvisors(), after);
}

这带来两个直接后果：① 排在工具 Advisor 内侧的日志、RAG、校验会每轮都执行； ② 排在它外侧的记忆只会看到循环开始与结束，看不到中间的工具消息。这也是为什么「记忆放环内」要把 order 调到大于 MIN + 300。

copy 的实现DefaultAroundAdvisorChain.java:169； 工具循环里的重新进入ToolCallingAdvisor.java:167。

同一个 Advisor 实例会被复用

Advisor 通常是无状态的单例。不要在实例字段里存「本次请求」的数据——并发请求会互相覆盖。 需要请求级状态就放 context，或者用 Reactor Context。

速查表

你要做的事 做法
改请求 / 记日志 实现 BaseAdvisor 的 before / after
拦截并直接返回 实现 CallAdvisor，不调 nextCall
调整内外层 改 getOrder()；越小越外

流式下做清理 同时处理 doOnCancel / doOnError

陷阱与窍门

日志打了两遍 / 工具执行了两次

因为Advisor 被注册了两次：默认 + 请求级各一次，或者工具 Advisor 自动注册之外又手动加了一个。 改成统一在一个地方注册，工具 Advisor 交给框架。

RAG 在带工具的对话里检索了好几次

因为QuestionAnswerAdvisor 的 order 是 0，位于工具 Advisor 内侧，工具循环每轮 都会重新进链。改成把 order 调到小于 MIN + 300，或者接受这个行为（每轮按最新 上下文重新检索）。

流式接口里 after 没执行，计费少了一条

因为BaseAdvisor 只在收到 finish reason 时调 after；取消或异常 不会触发。改成关键逻辑放到 doFinally 或观测层，别只依赖 after。

并发下 Auditor 记录的耗时忽大忽小

因为把开始时间存在 Advisor 的实例字段或 ThreadLocal 里，而 Advisor 是共享单例、 流式还会换线程。改成放到请求 context 里，或用 Observation。

07 · RAG 总览

RAG 不是「把文档丢给模型」，而是一条离线写入 + 在线检索的流水线：先把文档切块、向量化、存进 向量库；提问时再检索最相关的几块，拼进提示词。这一章把流水线的每一段和默认参数讲清楚，最后跑通一个 完全不依赖外部服务的本地 RAG。

读完你能做到

  • 画出 ETL 三段（Reader → Transformer → Writer）的输入输出，并说清 Document 在中间扮演什么角色
  • 解释为什么用 DeepSeek 做对话时，还必须另外引入一个 EmbeddingModel
  • 用 SimpleVectorStore + QuestionAnswerAdvisor 跑通「文档 → 问答」全流程
  • 调对 topK 与 similarityThreshold，并知道默认值意味着什么

先说为什么：模型不知道你的私有数据

模型的知识停留在训练截止时间，也不知道你公司的退货政策、产品手册和工单记录。两条路：微调，或者把相关资料 在提问时一起发给它。后者就是 RAG——便宜、可更新、可溯源，缺点是受上下文长度与检索质量限制。

RAG 里有两个模型，不是一个

ChatModel 负责读上下文并回答；EmbeddingModel 负责把文本变成向量。 两者是独立接口、独立 Bean、独立厂商。DeepSeek 的 starter 只提供 ChatModel，所以本站的 RAG 示例必须 额外引入一个 EmbeddingModel（下一节讲三种选法）。

ETL 流水线：三段，缺一不可

① Reader：把各种来源变成 Document
文本、PDF、Markdown、网页、数据库行，最终都变成带 text 与 metadata 的 Document。Document.java:120
② Transformer：切块、清洗、补元数据
最常用的是 TokenTextSplitter：按 token 切，默认块大小 800 token。 TokenTextSplitter.java:40
③ Writer：向量化并写入向量库
VectorStore 同时是 DocumentWriter 与 VectorStoreRetriever： 写入时算 embedding，检索时算 query embedding 再比相似度。 VectorStore.java:40

三段的接口都很小：DocumentReader 提供 get()， DocumentTransformer 是一个 Function<List<Document>, List<Document>>， VectorStore 提供 add / delete / similaritySearch。 这意味着你可以随意替换其中一段，而不影响另外两段。

切分粒度决定召回质量

块太大，检索命中后塞进提示词的内容里噪音多、还浪费 token；块太小，一句话被切断，语义不完整。 TokenTextSplitter 默认 800 token / 最小 350 字符，并且优先在 . ? ! 换行 处断开——这就是为什么它比「按字数硬切」更不容易切坏句子。

切分参数默认值TokenTextSplitter.java:42； apply 与 split 的关系TextSplitter.java:44。

EmbeddingModel：DeepSeek 之外还得再引一个

三种常见选法，按「要不要外部服务」排序：

方案 依赖 优点 代价
本地 ONNX（本章示例） spring-ai-starter-model-transformers 零 Key、零外部服务、数据不出机器 首次启动要下载模型；CPU 推理，吞吐有限
Ollama spring-ai-starter-model-ollama 本地、可换模型、有 GPU 加速 要装 Ollama 并 pull embedding 模型
OpenAI 兼容网关 spring-ai-starter-model-openai 质量稳定、无需本地资源 要 key；数据出境；按 token 计费

本章用本地 ONNX：配置前缀是 spring.ai.embedding.transformer，默认模型是 sentence-transformers/all-MiniLM-L6-v2，输出 384 维向量。第一次启动会从远程下载模型并缓存， 之后离线可用。 

spring:
  ai:
    embedding:
      transformer:
        cache:
          directory: ./.cache/spring-ai   # 模型缓存目录，默认是临时目录，重启会重新下载
        onnx:
          model-output-name: last_hidden_state

配置前缀TransformersEmbeddingModelProperties.java:41， 默认缓存目录是临时目录TransformersEmbeddingModelProperties.java:43。

不要把缓存目录留在默认的临时目录

默认目录是启动时创建的临时目录，进程重启后可能被清理，导致每次启动都重新下载模型。显式指定一个项目内或 用户目录下的路径，开发和 CI 都稳定得多。

最小可跑：本地文档 → 向量库 → 问答接口

package com.example.demo;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.client.advisor.vectorstore.QuestionAnswerAdvisor;
import org.springframework.ai.embedding.EmbeddingModel;
import org.springframework.ai.vectorstore.SearchRequest;
import org.springframework.ai.vectorstore.SimpleVectorStore;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class RagConfig {

    // 内存向量库：进程重启即清空，适合演示；生产换 pgvector / Redis / Milvus
    @Bean
    VectorStore vectorStore(EmbeddingModel embeddingModel) {
        return SimpleVectorStore.builder(embeddingModel).build();
    }

    @Bean
    ChatClient chatClient(ChatClient.Builder builder, VectorStore vectorStore) {
        return builder
                .defaultAdvisors(QuestionAnswerAdvisor.builder(vectorStore)
                        .searchRequest(SearchRequest.builder()
                                .topK(4)
                                .similarityThreshold(0.5)
                                .build())
                        .build())
                .build();
    }
}
package com.example.demo;

import java.util.List;

import org.springframework.ai.document.Document;
import org.springframework.ai.transformer.splitter.TokenTextSplitter;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.stereotype.Component;

@Component
class IngestRunner implements ApplicationRunner {

    private final VectorStore vectorStore;

    IngestRunner(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    @Override
    public void run(ApplicationArguments args) {
        List<Document> docs = List.of(
                new Document("退货政策：签收后 7 天内可无理由退货，商品需保持完好。"),
                new Document("运费规则：单笔满 99 元包邮，偏远地区除外。"),
                new Document("发票：支持电子发票，下单时填写抬头，发货后 24 小时内开具。"));

        var splitter = TokenTextSplitter.builder().build();
        this.vectorStore.add(splitter.apply(docs));
    }
}
@RestController
class AskController {

    private final ChatClient chatClient;

    AskController(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    @GetMapping("/ask")
    String ask(@RequestParam String q) {
        return this.chatClient.prompt().user(q).call().content();
    }
}

访问 /ask?q=满多少包邮，Advisor 会先检索出「运费规则」那一块，拼进提示词，再让模型基于它回答。

QuestionAnswerAdvisor：一个 Advisor 就是整条在线链路

它的 before() 只做四件事：

  1. 从提示词的最后一条 user 消息取问题（没有则为空字符串）；
  2. 用当前 SearchRequest 调 vectorStore.similaritySearch(...)；
  3. 把检索到的文档拼成 {question_answer_context}；
  4. 套进默认模板，替换最后一条 user 消息的文本（原问题已渲染进模板），再交给后面的链路。

默认模板长这样（原文）：

{query}

Context information is below, surrounded by ---------------------

---------------------
{question_answer_context}
---------------------

Given the context and provided history information and not prior knowledge,
reply to the user comment. If the answer is not in the context, inform
the user that you can't answer the question.

注意最后一句：它明确要求「上下文里没有就说不知道」。这比你自己写「不要编造」有效得多——因为它不是 system 消息，而是把检索上下文与约束一起塞进最后一条 user 消息；想换成中文或调整语气，用 .promptTemplate(...) 覆盖。

默认模板QuestionAnswerAdvisor.java:61； before 的检索与拼装QuestionAnswerAdvisor.java:109； 默认 order 是 0QuestionAnswerAdvisor.java:75。

SearchRequest：两个参数决定召回

参数 默认值 调大 / 调小会怎样
topK 4 调大：召回更全，但提示词更长、噪音更多、更贵
similarityThreshold 0.0（全收） 调大：只留高相似度，减少幻觉，但可能「什么都没检索到」
filterExpression 无 按 metadata 过滤，例如只查某个产品线、某个语言

默认值见 SearchRequest.java:49、 SearchRequest.java:44。

默认阈值 0.0 意味着「什么都收」

哪怕问题和文档毫不相关，前 4 条也会被塞进提示词。模型看到一堆无关内容，反而更容易编。生产环境通常把阈值 设在 0.5–0.75（取决于 embedding 模型与数据集），并把 topK 控制在 3–6。

运行时还可以按请求覆盖过滤条件：在 advisor 上下文里放 QuestionAnswerAdvisor.FILTER_EXPRESSION，before() 会用它替换默认过滤表达式。

端到端：一次提问到底发生了什么

  • ① 用户问题进入 Advisor 链
    QuestionAnswerAdvisor 的 order 是 0，位于工具 Advisor（MIN+300）内侧； 纯 RAG 调用没有工具，所以它等价于紧贴模型调用。带工具的对话里，它会在每轮工具循环中重新检索。
  • ② 问题向量化
    用写入时同一个 EmbeddingModel 把问题转成 384 维向量。
  • ③ 相似度检索
    SimpleVectorStore 对所有向量算余弦相似度，按分数降序，过滤阈值后取前 K 条。 SimpleVectorStore.java:156
  • ④ 拼提示词
    检索结果填进默认模板，追加到用户消息末尾。
  • ⑤ 调 ChatModel
    DeepSeek 只看到「问题 + 检索到的上下文」，它不知道向量库的存在。
  • ⑥ 返回答案
    回答里通常不会带出处；要展示引用，需要自己从检索结果里取 metadata。

    陷阱与窍门

    启动报「No EmbeddingModel bean」

    因为只引了 DeepSeek 的 starter，它只提供 ChatModel。改成再引一个 embedding provider（本章用 spring-ai-starter-model-transformers）。

    问了半天，模型总说「无法回答」

    因为阈值太高或切块太碎，检索没命中。改成先把 similarityThreshold 降到 0 看能不能召回，再逐步上调；同时检查切块后每块是否还保留完整语义。

    答非所问，但文档里明明有答案

    因为默认 topK=4 且阈值 0，无关块挤占了上下文。改成加 metadata 过滤（产品线、版本、语言），或先把文档按主题分库，别把所有内容塞进一个库。

    入库很慢

    因为SimpleVectorStore.doAdd 是逐条调用 embeddingModel.embed(document)，不是批量。文档多时要么换支持批量的向量库，要么自己分批并发。 SimpleVectorStore.java:115

    先做「能召回」，再做「答得好」

    调 RAG 的顺序应该是：检索结果对不对 → 提示词有没有把它们用上 → 回答有没有超出上下文。先盯着最终答案调 提示词，通常是在错误的地基上盖楼。

    自检三问

    1. 为什么 ChatModel 和 EmbeddingModel 必须分开引？换 embedding 模型会影响什么？
    2. similarityThreshold = 0 时，检索结果会发生什么？为什么这可能导致幻觉？
    3. 切块大小从 800 调到 200，召回与回答质量可能分别怎么变？

    20 分钟动手练习

    1. 把 topK 从 4 改成 1 和 10，问同一个问题，对比回答与 token 用量。
    2. 给每个 Document 加 metadata（如 category=refund），用过滤表达式只查退款政策。
    3. 把阈值调到 0.9，观察「无法回答」出现频率，再降回 0.5，记录差异。

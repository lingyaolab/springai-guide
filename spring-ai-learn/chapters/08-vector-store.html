08 · Embedding 与向量库选型

向量库不是「装个数据库」，它有三个必须一次性想清楚的约束：维度决定表结构、 距离度量决定排序、索引类型决定召回率与延迟。换 embedding 模型往往意味着 整库重建，所以这一章先把约束讲清，再给选型表。

读完你能做到

  • 说清 EmbeddingModel 的四个方法与 dimensions() 的真实开销
  • 解释为什么换 embedding 模型必须重建索引，以及维度不匹配会在哪一步报错
  • 在余弦、欧氏、内积三种度量之间做出有依据的选择
  • 用 pgvector 建表、建 HNSW 索引，并知道 initialize-schema 该设什么

先说为什么：向量库 = 存储 + 索引 + 度量

很多人把向量库当成「能存 float 数组的数据库」。真正决定检索质量的，是三者一起：

存储：向量 + 原文 + metadata
原文用于拼提示词，metadata 用于过滤（产品线、语言、版本）。
索引：HNSW / IVFFlat / FLAT
近似最近邻（ANN）用一点召回率换数量级的速度。数据量小的时候，暴力扫描反而更准。
度量：cosine / euclidean / inner product
排序规则的数学定义，必须与 embedding 模型的训练方式匹配。
为什么「换模型 = 重建库」

向量的每一维含义由模型决定。模型 A 的第 7 维和模型 B 的第 7 维毫无关系，两个模型产出的向量放在一起比较 没有意义；维度也可能不同（384 / 768 / 1536 / 3072）。所以变更 embedding 模型时，必须把全部文档重新 embed 一遍，写入新表或清空旧表。

EmbeddingModel：四个方法，一个隐藏成本

方法 用途
embed(String) 单条文本 → float[]
embed(Document) 按 metadata 模式拼内容后 embed
embed(List<String>) 批量，返回 List<float[]>
embedForResponse(List<String>) 批量并保留 usage 等元数据
dimensions() 默认实现会真的调一次远程接口（embed 一个 "Test String"） 
default int dimensions() {
    return embed("Test String").length;
}

接口定义EmbeddingModel.java:39； dimensions() 的默认实现EmbeddingModel.java:137。

启动时莫名多了一次（甚至计费的）embedding 调用

原因通常是向量库在初始化时问 embeddingModel.dimensions()，而默认实现会真的请求一次。 已知维度时，在自定义 EmbeddingModel 里覆盖 dimensions()，或在向量库配置里显式 写 dimensions，就能避免。

维度对齐：三个数字的关系

以 pgvector 为例，建表语句里的 vector(N) 决定了这一列能存多少维：

CREATE TABLE IF NOT EXISTS vector_store (
    id        uuid PRIMARY KEY,
    content   text,
    metadata  json,
    embedding vector(1536)
);

N 从哪来？按优先级：

  • ① 配置显式指定
    spring.ai.vectorstore.pgvector.dimensions，默认是 -1（未指定）。 PgVectorStoreProperties.java:37
  • ② 问 embedding 模型
    调 embeddingModel.dimensions()；all-MiniLM-L6-v2 是 384，OpenAI text-embedding-3-small 是 1536。 PgVectorStore.java:505
  • ③ 兜底 1536
    只有 embeddingModel.dimensions() 抛异常时才会打 warn 并回退到 OpenAI 的默认维度； 返回非正数时则静默落到同一个兜底值。这个兜底很危险：模型是 384 维时，表会被建成 1536 维， 写入直接失败。 PgVectorStore.java:511
    • 模式校验默认是关的

    spring.ai.vectorstore.pgvector.schema-validation 默认 false。开启后，表已存在 但维度不一致时会明确抛「Actual vector dimensions is X, required vector dimensions is Y」，而不是在写入时 报一个难懂的 SQL 错误。生产环境建议打开。

    维度不一致的抛错点PgVectorSchemaValidator.java:160。

    距离度量：三种，别选错

    度量 直觉 适用
    COSINE_DISTANCE 只看方向，不看长度 文本 embedding 的默认选择，大多数模型适用
    EUCLIDEAN_DISTANCE 直线距离 向量已归一化时与余弦等价；图像特征常用
    NEGATIVE_INNER_PRODUCT 点积越大越相似 模型明确要求内积、且向量已归一化时性能最好

    pgvector 的默认是余弦距离，索引操作符类也随之确定（vector_cosine_ops）。度量与索引 是一起建的：改了度量，索引必须重建，否则查询用不上索引，退化成全表扫描。

    默认度量与索引类型PgVectorStoreProperties.java:39PgVectorStoreProperties.java:41； 建索引语句PgVectorStore.java:454。

    选型：先问「你已有什么」

    向量库 starter 适合 代价
    pgvector spring-ai-starter-vector-store-pgvector 已有 PostgreSQL；要事务、SQL、备份一体化 千万级以上需要分区/调参；HNSW 建索引慢
    Redis spring-ai-starter-vector-store-redis 低延迟、已有 Redis、要 TTL 依赖 RedisJSON + RediSearch 模块
    Milvus spring-ai-starter-vector-store-milvus 亿级向量、专业向量检索 独立集群，运维成本最高
    Elasticsearch / OpenSearch ...-elasticsearch / ...-opensearch 已有搜索集群，要混合检索（BM25 + 向量） 索引 mapping 与内存调优复杂
    SimpleVectorStore 无（手动建 Bean） 演示、单机小数据、测试 纯内存、暴力扫描、重启即丢
    默认建议

    已经有 PostgreSQL 就用 pgvector：少一个组件、能和业务数据一起备份、SQL 过滤 metadata 很自然。 只有在「向量规模上亿」或「延迟要求极苛刻」时，才值得引入独立向量库。

    pgvector：一条命令起库，四行配置接上

    docker run -d --name pgvector -p 5432:5432 \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=vectordb \
  pgvector/pgvector:pg17
    spring:
  ai:
    vectorstore:
      pgvector:
        initialize-schema: true        # 演示用；生产建议 false，由 Flyway 管
        dimensions: 384                # all-MiniLM-L6-v2；不写则问模型
        index-type: HNSW               # HNSW / IVFFLAT / NONE
        distance-type: COSINE_DISTANCE
        schema-validation: true
        table-name: vector_store
        max-document-batch-size: 10000

    initialize-schema=true 时，启动会依次执行：创建 vector / hstore / uuid-ossp 扩展 → 建 schema → 建表 → 建索引。所以数据库账号需要有建扩展的权限。

    默认表名与批量上限PgVectorStore.java:165、 PgVectorStore.java:175； 建扩展与建表PgVectorStore.java:429。

    配置项默认值有一个坑：initialize-schema 默认是 false

    向量库的通用属性默认不建表，需要显式 opt-in。第一次跑 demo 忘了开，典型报错是 relation "vector_store" does not exist。 CommonVectorStoreProperties.java:33

    批量写入：8191 与 90%

    一次 embedding 请求能带的 token 数有上限。默认的 TokenCountBatchingStrategy 按 8191 token 估算，并预留 10% 作为安全余量，也就是实际按约 7371 token 分批。 

    @Bean
BatchingStrategy batchingStrategy() {
    return new TokenCountBatchingStrategy(
            EncodingType.CL100K_BASE,
            4000,          // 更保守的输入上限
            0.1);          // 预留 10%
}

    它没有 builder，只能走构造器——这是读源码才会发现的细节，别照抄成 TokenCountBatchingStrategy.builder()。其中 EncodingType 来自 com.knuddels.jtokkit.api，BatchingStrategy 来自 org.springframework.ai.embedding。

    默认 token 上限TokenCountBatchingStrategy.java:59， 预留比例TokenCountBatchingStrategy.java:65。

    分批与限流是两回事

    分批解决「单次请求太大」，不解决「每秒请求太多」。厂商侧通常还有 RPM / TPM 限流，入库几十万文档时要 自己加并发控制与重试退避。

    迁移与运维：换模型时怎么不炸

    1. 新表 + 双写：用新维度建一张新表，后台重新 embed 全部文档，写完切读流量。
    2. 不要原地改列：ALTER TABLE ... TYPE vector(768) 在数据量大时非常慢，且旧向量本身已失效。
    3. 保留原文：content 字段必须存，否则换模型时无法重新 embedding。
    4. 记录模型版本：在 metadata 里写 embedding_model，排查「为什么这两条不相似」时非常有用。

    速查表

    你要做的事 写法
    看模型维度 embeddingModel.dimensions()（会真调一次）
    显式指定维度 spring.ai.vectorstore.pgvector.dimensions=384
    首次建表 initialize-schema=true
    打开模式校验 schema-validation=true
    换索引类型 index-type=HNSW / IVFFLAT / NONE
    换度量 distance-type=COSINE_DISTANCE / EUCLIDEAN_DISTANCE / NEGATIVE_INNER_PRODUCT
    改批量 自定义 BatchingStrategy Bean

    陷阱与窍门

    启动报 relation "vector_store" does not exist

    因为initialize-schema 默认 false。改成首次设为 true， 或先用迁移脚本建表再设回 false。

    写入报维度不匹配

    因为表是按 1536 建的，模型输出 384（或反过来）。改成显式设置 dimensions，并开启 schema-validation 让问题在启动时就暴露。

    换了 embedding 模型，检索结果全乱

    因为新旧向量在同一个空间里比较。改成换模型必须全量重 embed， 不能只换配置。

    查询慢，但数据量不大

    因为度量与索引操作符类不匹配，或者根本没建索引（index-type=NONE）。 改成确认索引存在且使用对应 *_ops，用 EXPLAIN 看是否走索引。

    metadata 过滤比调 topK 更有效

    当你有明确的业务维度（租户、产品线、语言、版本）时，先过滤再排序，比把 topK 调大再指望模型自己挑 更稳、更便宜。

09 · 高级检索

第 07 章的 RAG 只有两个旋钮：topK 和阈值。真实业务里，问题往往出在查询本身不完整 （「那它呢」）、库里混了不该检索的内容（别的租户、旧版本）、召回了但排序不对。 这一章把四类手段逐个讲清：过滤、改写、多路召回、重排。

读完你能做到

  • 用 metadata 过滤把检索范围收窄到「当前租户 + 当前版本」，而不是事后让模型筛
  • 解释多轮对话里为什么必须先改写查询，以及改写带来的额外 LLM 调用成本
  • 用 MultiQueryExpander 做多路召回，并知道结果如何合并去重
  • 用 RetrievalAugmentationAdvisor 把改写、召回、重排、拼装串成一条可配置的流水线

先说为什么：检索质量 = 查询 × 范围 × 排序

模型只能基于你给它的上下文回答。上下文错了，提示词写得再好也没用。检索质量可以拆成三个乘数：

查询：用户那句话适不适合检索
「那它呢」「再详细点」单独拿去检索，几乎必然召回错误内容。
范围：该不该在这个库里查
多租户、多版本、多语言混在一个索引里，topK 再准也会串。
排序：相似度高 ≠ 最有用
向量相似度是粗排，真正决定答案质量的是精排（rerank）。

metadata 过滤：先缩小范围，再谈相似度

SearchRequest 支持两种过滤写法：字符串 DSL 和 Filter.Expression。字符串形式类似 SQL 的 where： 

country == 'UK' && year >= 2020 && isActive == true

官方示例vectordbs.adoc:165。

但拼接字符串容易出注入与转义问题。更稳的是用 FilterExpressionBuilder 构造： 

Filter.Expression filter = new FilterExpressionBuilder()
        .and(
                new FilterExpressionBuilder().eq("tenant", tenantId).build(),
                new FilterExpressionBuilder().gte("version", 2).build())
        .build();

List<Document> docs = vectorStore.similaritySearch(
        SearchRequest.builder().query(q).topK(4).filterExpression(filter).build());

eq/ne/gt/gte/lt/lte/in/nin/and/or 都在 FilterExpressionBuilder.java:60。

哪些字段适合放 metadata

高基数、强约束、经常用来「排除」的字段：租户 ID、产品线、文档版本、语言、权限级别、生效日期。 不要把整段正文塞进 metadata——它不会参与相似度计算，只会让索引变大。

查询改写：把「那它呢」变成可检索的问题

多轮对话里，用户第二句往往依赖上一句。直接拿它去检索向量库，召回的多半是无关内容。 RewriteQueryTransformer 会先让模型把问题改写成独立、完整、适合检索的句子。 

var rewrite = RewriteQueryTransformer.builder()
        .chatClientBuilder(ChatClient.builder(chatModel))
        .build();

// 输入：「那退款呢？」（上文在聊运费）
// 输出：「退款政策和退款流程是什么？」

它的默认提示词里有一个 {targetSearchSystem}，默认值是 "vector store"， 意思是「按向量库检索的习惯来改写」。你可以换成自己的领域描述，让改写更贴近业务词汇。

默认目标系统RewriteQueryTransformer.java:55。

改写是「多一次 LLM 调用」

每次提问都会先调一次模型做改写，再调一次模型生成答案。延迟和成本都翻倍。优化方式：只在检测到指代词/短问句时 才改写，或用一个更小更快的模型专门做改写。

多查询扩展：一次提问，召回多路结果

用户的措辞和文档的措辞经常对不上（「包邮」vs「免运费」）。MultiQueryExpander 让模型生成几个 语义相近但措辞不同的查询，分别检索，再合并。 

var multiQuery = MultiQueryExpander.builder()
        .chatClientBuilder(ChatClient.builder(chatModel))
        .numberOfQueries(3)      // 默认 3
        .includeOriginal(true)   // 默认 true：原始查询也算一路
        .build();

RetrievalAugmentationAdvisor 内部的执行顺序是：

  1. 逐个 QueryTransformer 改写；
  2. QueryExpander 展开成 N 个查询；
  3. 每个查询并行走一次检索（用 CompletableFuture）；
  4. DocumentJoiner 合并结果；
  5. 后处理（重排）；
  6. 拼进提示词。

默认条数与是否保留原查询MultiQueryExpander.java:74； 并行检索与合并RetrievalAugmentationAdvisor.java:129。

合并时按什么去重

默认的 ConcatenationDocumentJoiner 按 Document 的 id 去重， 保留第一次出现的那条。所以同一段文档被多个查询命中时不会重复塞进上下文，但分数也不会被「投票加权」—— 想做 RRF / 加权融合，要自己实现 DocumentJoiner。 ConcatenationDocumentJoiner.java:58

翻译与压缩：两个特定场景的改写

翻译：跨语言检索

var translate = TranslationQueryTransformer.builder()
    .chatClientBuilder(ChatClient.builder(chatModel))
    .targetLanguage("english")
    .build();

知识库是英文、用户用中文提问时，把查询翻成英文再检索。目标语言必填，否则构造时断言失败。

压缩：长对话里的指代

var compress = CompressionQueryTransformer.builder()
    .chatClientBuilder(ChatClient.builder(chatModel))
    .build();

把「历史 + 追问」压成一个自包含的问题，比单纯改写更适合多轮长对话。

翻译的目标语言必填TranslationQueryTransformer.java:74； 压缩的默认提示词CompressionQueryTransformer.java:50。

不要在一条链上叠满所有 Transformer

改写 + 翻译 + 压缩 + 多查询，一次提问可能触发 5 次以上 LLM 调用。按场景选 1–2 个就够： 多轮对话用压缩或改写；跨语言用翻译；术语不匹配用多查询。

VectorStoreDocumentRetriever：默认值仍然是「全收」

参数 不传时 说明
similarityThreshold 0.0 接受所有结果
topK 4 每个查询各取 4 条
filterExpression null 不过滤

第三项支持 Supplier<Filter.Expression>，意味着可以在每次请求时根据当前用户 动态计算过滤条件（租户、权限），而不是在启动时写死。 

var retriever = VectorStoreDocumentRetriever.builder()
        .vectorStore(vectorStore)
        .similarityThreshold(0.6)
        .topK(4)
        .filterExpression(() -> new FilterExpressionBuilder()
                .eq("tenant", TenantContext.current())
                .build())
        .build();

默认值VectorStoreDocumentRetriever.java:79； 请求级过滤上下文 key 是 vector_store_filter_expressionVectorStoreDocumentRetriever.java:59。

重排：框架只给钩子，不替你选模型

向量相似度适合「粗排」，因为它只看语义距离，不考虑问题与段落的逐词匹配、时效性、权威性。精排通常在召回之后 用另一个模型（cross-encoder 或 LLM）重新打分。

Spring AI 2.0.2 没有内置 reranker，只提供 DocumentPostProcessor 这个钩子： 

class LlmRerankPostProcessor implements DocumentPostProcessor {

    private final ChatClient chatClient;

    LlmRerankPostProcessor(ChatModel chatModel) {
        this.chatClient = ChatClient.builder(chatModel).build();
    }

    @Override
    public List<Document> process(Query query, List<Document> documents) {
        // 让模型按「与问题的相关度」重新排序，返回前 N 条
        // 真实项目建议用专门的 rerank 模型，别用生成模型硬排
        return documents.stream().limit(5).toList();
    }
}

调用顺序是：召回 → 每个 DocumentPostProcessor 依次处理 → 拼进提示词。所以重排可以改顺序、 过滤、甚至替换文档内容。

没有 rerank 也能做的三件事

① 用 metadata 过滤排除低质来源；② 把 topK 调大后再按业务规则截断；③ 在文档入库时就把 「权威度」「更新时间」写进 metadata，排序时加权。这三件事比堆一个 LLM 重排更便宜、更可控。

组装：一条可配置的检索流水线

@Bean
Advisor ragAdvisor(ChatModel chatModel, VectorStore vectorStore) {
    var rewrite = RewriteQueryTransformer.builder()
            .chatClientBuilder(ChatClient.builder(chatModel))
            .build();

    var multiQuery = MultiQueryExpander.builder()
            .chatClientBuilder(ChatClient.builder(chatModel))
            .numberOfQueries(3)
            .build();

    var retriever = VectorStoreDocumentRetriever.builder()
            .vectorStore(vectorStore)
            .similarityThreshold(0.6)
            .topK(4)
            .build();

    return RetrievalAugmentationAdvisor.builder()
            .queryTransformers(rewrite)
            .queryExpander(multiQuery)
            .documentRetriever(retriever)
            .queryAugmenter(ContextualQueryAugmenter.builder()
                    .allowEmptyContext(false)   // 默认就是 false
                    .build())
            .build();
}

before 的七步流程RetrievalAugmentationAdvisor.java:107； allowEmptyContext 默认 falseContextualQueryAugmenter.java:77。

allowEmptyContext=false 的含义是：没检索到任何文档时，把用户问题替换成一段 「超出知识库范围」的固定提示，再交给模型生成拒答。模型仍会被调用一次， 只是拿不到空上下文，从而降低「没资料还硬编」的概率。想连这次调用都省掉，需要在 Advisor 之前短路。

把出处带回前端

检索到的文档不会凭空消失：RetrievalAugmentationAdvisor 把它们放进请求上下文的 rag_document_context，流式/同步响应里都能拿到。要做「答案 + 引用」，就从这里取。 

ChatClientResponse response = chatClient.prompt()
        .user(q)

陷阱与窍门

多轮对话里检索结果越来越差

因为拿「那它呢」这类不完整的问题去检索。改成加 CompressionQueryTransformer 或 RewriteQueryTransformer，并接受多一次模型调用。

A 租户搜到了 B 租户的文档

因为只在提示词里说「只回答本公司内容」，没有在检索层过滤。改成用 filterExpression 在向量库层强制隔离，提示词只作为第二道防线。

开了多查询后偶尔重复引用同一段

因为合并按 id 去重，但如果你在入库时每次生成新 id，同一段内容会被当成不同文档。 改成用内容哈希或稳定的业务主键作为 Document id。

延迟从 1 秒涨到 5 秒

因为改写 + 多查询意味着 1 次改写调用 + 3 路检索 + 1 次回答。改成 按场景裁剪链路，给每一步设超时，并把改写结果缓存（相同问题短时间内复用）。

自检三问

  1. 为什么「让模型只回答本公司内容」不能替代 metadata 过滤？
  2. MultiQueryExpander 默认生成几条查询？合并时按什么去重？
  3. allowEmptyContext=false 在检索为空时改变了什么？模型还会被调用吗？

20 分钟动手练习

  1. 给文档加 tenant metadata，用 FilterExpressionBuilder 做租户隔离，验证跨租户查不到。
  2. 连续问两轮：「退货政策是什么？」→「那运费呢？」，对比加不加改写时第二次的召回结果。
  3. 把 numberOfQueries 从 3 改成 5，记录召回条数、延迟与最终答案质量的变化。

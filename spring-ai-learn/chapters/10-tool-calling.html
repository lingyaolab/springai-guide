10 · Tool Calling

工具调用的本质是一个协议：模型不执行你的代码，它只返回「我要调用 get_weather， 参数是 {"city":"杭州"}」；真正执行的是框架，把结果再发回给模型。理解这个分工， 才能理解为什么「工具没被调用」「参数是 null」「异常没抛出来」都有各自不同的原因。

读完你能做到

  • 用一个 @Tool 方法跑通「模型决定调用 → 框架执行 → 模型总结」的完整循环
  • 说清 ToolCallingAdvisor 与 ToolCallingManager 的分工，以及循环什么时候结束
  • 用 ToolContext 把 userId / tenantId 这类业务上下文传给工具，而不塞进提示词
  • 解释工具异常为什么默认不抛给调用方，以及 40 / 150 两个调用上限从哪来

先说为什么：模型只「提议」，你负责「执行」

模型没有你的 JVM、数据库和文件系统。它能做的只有一件事：在响应里返回一个结构化的 tool_calls 数组，告诉你「我想调哪个函数、参数是什么」。执行权始终在你这边。

① 你注册工具定义
名字、描述、参数 JSON Schema 随请求一起发给模型。 ToolDefinitions.java:52
② 模型返回 tool_calls
它只输出「调用意图」，不接触你的代码。
③ 框架执行并回填结果
ToolCallingManager 找到对应 ToolCallback，反射调用你的方法，把返回值作为 tool 消息追加进对话。 DefaultToolCallingManager.java:178
④ 带着结果再问一次模型
模型看到工具结果，生成最终回答；如果它还想调工具，循环继续。
为什么工具描述比方法名重要

模型选不选这个工具，主要看 description 和参数 schema，而不是方法名。描述写得含糊 （「查询数据」），模型就不知道该在什么时候用；描述写得具体（「按城市名查询当前天气，返回温度与天气现象」）， 命中率会明显提高。

最小可跑：一个天气工具

package com.example.demo;

import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.annotation.ToolParam;
import org.springframework.stereotype.Component;

@Component
class WeatherTools {

    @Tool(description = "按城市名查询当前天气，返回温度和天气现象")
    String currentWeather(
            @ToolParam(description = "城市名，例如杭州、北京") String city) {
        // 真实项目里这里调气象 API；示例直接返回固定值
        return city + "：18℃，多云";
    }
}
@Service
class ChatService {

    private final ChatClient chatClient;
    private final WeatherTools weatherTools;

    ChatService(ChatClient.Builder builder, WeatherTools weatherTools) {
        this.chatClient = builder.build();
        this.weatherTools = weatherTools;
    }

    String ask(String question) {
        return this.chatClient.prompt()
                .user(question)
                .tools(this.weatherTools)
                .call()
                .content();
    }
}

问「杭州今天要带伞吗？」，实际会发生两次模型调用：第一次返回 tool_calls，框架执行 currentWeather("杭州")，第二次把结果带回模型，模型再生成「不用带伞」这类回答。

逐行解读：注解里的四个字段

字段 作用 不写会怎样
name 工具名，默认取方法名 方法名带空格或括号时，部分厂商会拒绝
description 给模型看的用途说明 模型只能靠名字猜，命中率下降
returnDirect 为 true 时结果直接返回给调用方，不再问模型 默认 false，结果会回填给模型再总结一次
resultConverter 把返回值转成字符串的策略 默认用 Jackson 序列化对象

注解字段定义Tool.java:54； 工具名建议只用字母、数字、下划线、连字符和点Tool.java:42。

参数的 schema 不是手写的：框架会扫描方法签名，把参数名、类型、@ToolParam 的描述与是否必填 一起生成 JSON Schema。默认所有参数必填；加 required = false 或 @Nullable 才会变成可选。 

{
  "type": "function",
  "function": {
    "name": "currentWeather",
    "description": "按城市名查询当前天气，返回温度和天气现象",
    "parameters": {
      "type": "object",
      "properties": { "city": { "type": "string", "description": "城市名，例如杭州、北京" } },
      "required": ["city"]
    }
  }
}
工具方法不能返回函数类型

如果方法返回 Function / Supplier / Consumer，框架会打一条 warn 并忽略这个方法——因为它无法把函数序列化成工具结果。返回 DTO、字符串、列表都可以。 MethodToolCallbackProvider.java:110

循环：ToolCallingAdvisor 什么时候停

2.0 起，工具循环从 ChatModel 内部搬到了 ToolCallingAdvisor。它由 DefaultChatClient 自动注册，order 是 HIGHEST_PRECEDENCE + 300， 所以你不需要、也不应该再手动 .advisors(ToolCallingAdvisor.builder().build())。 

do {
    // 1. 带上工具定义，调用模型
    response = callAdvisorChain.copy(this).nextCall(request);

    // 2. 判断响应里有没有 tool_calls
    isToolCall = toolExecutionEligibilityChecker.isToolCallResponse(response);

    if (isToolCall) {
        // 3. 执行工具，把 tool 消息拼回历史
        result = toolCallingManager.executeToolCalls(
                new Prompt(fullTurnHistory, options), response);
        instructions = result.conversationHistory();
    }
} while (isToolCall);   // 4. 直到模型不再要求调工具

循环实现ToolCallingAdvisor.java:149， order 常量ToolCallingAdvisor.java:75； 官方对循环步骤的描述tools.adoc:224。

「模型没调用工具」先查这三件事

① 工具描述是否说清了「什么时候用」；② 参数 schema 是否有必填项但模型不知道该填什么；③ 是否把工具加到了 这次请求（.tools(...)）或客户端的默认工具（.defaultTools(...)）上。 注意 .tools() 是追加到默认工具，不是替换。

ToolContext：业务上下文不要塞进提示词

用户 ID、租户 ID、请求追踪号这类信息不该让模型看到，也不该出现在参数 schema 里。做法是：方法多声明一个 ToolContext 参数，调用时通过 .toolContext(...) 传入。 

@Tool(description = "查询当前租户下指定状态的订单")
List<Order> myOrders(
        @ToolParam(description = "订单状态：PAID / SHIPPED / CLOSED") String status,
        ToolContext context) {
    String tenantId = (String) context.getContext().get("tenantId");
    return orderRepository.findByTenantAndStatus(tenantId, status);
}
String answer = chatClient.prompt()
        .user("我有哪些已发货的订单？")
        .tools(orderTools)
        .toolContext(Map.of("tenantId", "acme"))
        .call()
        .content();
方法声明了 ToolContext，但调用时没传

框架会直接抛 IllegalArgumentException: ToolContext is required by the method as an argument， 而不是把 null 传进去。这是有意的：让错误在第一次调用就暴露，而不是让工具悄悄用错租户。 MethodToolCallback.java:130

默认工具上下文（defaultToolContext）与调用级 toolContext 会合并， 调用级覆盖同名 key。适合把「固定租户」放默认值、「本次请求 ID」放调用级。

异常：默认不抛，而是回给模型

工具方法抛异常时，默认行为不是把异常抛给你的 Controller，而是把异常信息包装成一条 tool 响应发回模型，让模型决定怎么处理（道歉、换参数重试、换个工具）。 

// DefaultToolExecutionExceptionProcessor 的默认配置
private static final boolean DEFAULT_ALWAYS_THROW = false;

默认不抛DefaultToolExecutionExceptionProcessor.java:41； 想改成抛给调用方，设 spring.ai.tools.throw-exception-on-error=trueToolCallingProperties.java:65。

默认：回给模型

  • 模型能看到「参数不合法」「库存不足」这类信息
  • 可以自己修正参数再试
  • 风险：错误被「圆」过去，调用方以为成功

throw-exception-on-error=true

  • 异常直接冒泡到你的业务代码
  • 适合资金、扣库存等不能重试的操作
  • 需要自己处理重试与幂等

调用上限：40 与 150

工具循环是 do-while，如果模型反复要求调用同一个工具，没有上限就会无限烧 token。 2.0.2 内置了两个默认限制：

限制 默认值 作用范围
单个工具调用次数 40 一轮对话内，同一个工具最多 40 次
工具调用总次数 150 一轮对话内，所有工具合计最多 150 次
超限行为 THROW 抛 ToolCallLimitExceededException；可改成返回错误响应 
spring:
  ai:
    tools:
      throw-exception-on-error: false
      limits:
        max-calls-per-tool-default: 40
        max-total-tool-calls: 150
        on-limit-exceeded: THROW      # 或 RETURN_ERROR_RESPONSE
        # max-calls-per-tool:
        #   searchDocs: 5

默认上限DefaultToolCallingManager.java:100、 DefaultToolCallingManager.java:107； 配置项与默认值ToolCallingProperties.java:101。

记忆在环内还是环外

工具循环会产生 tool_calls 与 tool 消息。这些要不要进记忆，取决于记忆 Advisor 的 order：

位置 order 记忆里留下什么
环外（默认） HIGHEST_PRECEDENCE + 200 只留最终 user 与 assistant 消息，工具过程全部丢弃
环内 大于 +300（如 +400） 连 tool_calls 与工具结果一起保存，下一轮模型能看到「上次试过什么」

放进环内时，ToolCallingAdvisor 的内部历史需要关掉，否则会重复写入。用自动注册的 Advisor 时 框架会自动检测环内的 MemoryAdvisor 并关闭，不需要你配置。

不是所有存储都能存工具消息

2.0 内置实现里，InMemoryChatMemoryRepository、Redis 和 Neo4j 支持完整的工具消息； JDBC 仓库目前不支持。把 JDBC + 环内记忆组合使用，会遇到反序列化或丢消息的问题。 tools.adoc:294

流式工具调用：参数是碎片拼起来的

流式模式下，模型返回的 tool_calls 不是一次到齐的：函数名可能第一块就来，参数 JSON 会被拆成 很多 delta 片段。DeepSeek 用一个专门的 helper 把相邻 chunk 合并，拼成完整的工具调用后才执行。 

public ChatCompletionChunk merge(@Nullable ChatCompletionChunk previous, ChatCompletionChunk current) { ... }

合并逻辑DeepSeekStreamFunctionCallingHelper.java:43； 流式请求走 WebClientDeepSeekApi.java:177。

对业务代码来说这是透明的：.stream().content() 仍然只吐出最终文本。但如果你在流式过程中做进度提示， 不要指望能看到工具参数——工具执行发生在流结束之后、第二次模型调用之前。

returnDirect：跳过第二次模型调用

有些工具的返回值本身就是最终答案，不需要模型再总结一遍（例如「把这段文本原样返回」「生成下载链接」）。 把 returnDirect 设为 true，框架执行完工具后直接返回，省掉一次模型调用。 

@Tool(description = "生成报表下载链接", returnDirect = true)
String exportReport(@ToolParam(description = "报表日期，格式 yyyy-MM-dd") String date) {
    return "https://internal.example.com/reports/" + date + ".xlsx";
}

字段定义Tool.java:64； Advisor 里的短路分支ToolCallingAdvisor.java:198。

陷阱与窍门

同一条链上出现两个 ToolCallingAdvisor

因为2.0 会自动注册一个，你又手动加了一个，工具会执行两次。 改成删掉手动注入；需要定制时，用 spring.ai.chat.client.tool-calling.advisor-order 或提供一个 ToolCallingAdvisor.Builder Bean。

工具报错，但接口返回 200，内容是「抱歉，查询失败」

因为默认 throwExceptionOnError=false，异常被转成消息回给模型，模型把它「圆」了过去。 改成关键业务工具设 spring.ai.tools.throw-exception-on-error=true，并在工具内部 做幂等与参数校验。

工具没被调用，模型直接编了一个答案

因为描述太笼统，或者工具根本没进这次请求。改成把 description 写成 「在什么场景下用、返回什么」，并确认 .tools(...) / .defaultTools(...) 生效。

调用了错误的租户 / 越权

因为把 tenantId 当成工具参数，让模型填。改成用 ToolContext 传，模型永远看不到也不可篡改。

工具数量到 30+ 时，考虑渐进式披露

默认每轮把所有工具定义都发给模型，工具多了会挤占上下文、降低选择准确率。2.0.2 提供了 ToolSearchToolCallingAdvisor，先让模型「搜索工具」，只注入相关的那几个。

自检三问

  1. 模型知道你的 Java 方法实现吗？它决定的是什么、不决定什么？
  2. 一次带工具的对话，最少会调用几次模型？returnDirect = true 时会变成几次？
  3. 记忆 Advisor 的 order 从 200 改成 400，记忆里会多出哪两类消息？为什么 JDBC 仓库不适合这个组合？

20 分钟动手练习

  1. 把 currentWeather 的 description 改成「查询数据」，对比模型是否还会调用它。
  2. 让工具故意抛异常，分别在 throw-exception-on-error=false/true 下观察返回值差异。
  3. 给工具加一个 ToolContext 参数，调用时传 tenantId，验证模型无法篡改这个值。

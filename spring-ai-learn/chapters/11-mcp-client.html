11 · MCP 客户端

MCP（Model Context Protocol）把「工具」从你的 Java 方法扩展成任意进程或服务提供的能力。 对 Spring AI 来说，接入之后它们仍然是 ToolCallback——模型和工具循环完全感知不到区别。 这一章讲清三种传输、配置、工具发现与安全边界。

读完你能做到

  • 说清 stdio、SSE、Streamable HTTP 三种传输分别适合什么场景
  • 用 stdio 接入一个本地 MCP server，并让 ChatClient 用上它的工具
  • 解释 MCP 工具与本地 @Tool 的重名风险，以及 McpToolFilter 怎么兜底
  • 判断一个 MCP server 该不该接、以什么权限接

先说为什么：MCP 是「工具的 USB 接口」

没有 MCP 时，每接一个外部能力（文件系统、数据库、浏览器、SaaS），你都要为它写一套适配代码。 MCP 定义了统一的发现与调用协议：客户端问「你有哪些工具」，服务端返回工具清单与参数 schema， 调用时按名字传 JSON。

MCP Server：能力的提供方
可以是本地进程（stdio），也可以是远程服务（SSE / Streamable HTTP）。
MCP Client：Spring AI 这一侧
负责握手、发现工具、转发调用、处理超时与重连。
适配层：ToolCallbackProvider
自动装配把 MCP 工具包装成 SyncMcpToolCallbackProvider，于是 .tools(provider) 就能用。 McpToolCallbackAutoConfiguration.java:71

三种传输：先选连接方式

传输 怎么连 适合 注意
stdio 启动一个本地子进程，用标准输入输出通信 本地工具：文件系统、Git、SQLite、命令行 进程以你的权限运行；stdout 被协议占用
SSE HTTP 长连接，服务端推送事件 已有的远程 MCP 服务 连接要保活；网关可能缓冲
Streamable HTTP 普通 HTTP + 流式响应 新部署的远程服务（MCP 新版推荐） 需要服务端支持该规范
选型一句话

工具跑在用户机器上、需要访问本地文件 → stdio；工具是一个团队共享的服务 → Streamable HTTP； 只有老服务支持 SSE 时 → SSE。三种可以同时配，客户端会聚合成一个工具列表。

最小可跑：接入本地文件系统工具

加一个依赖：

    <dependency>
      <groupId>org.springframework.ai</groupId>
      <artifactId>spring-ai-starter-mcp-client</artifactId>
    </dependency>
spring:
  ai:
    mcp:
      client:
        enabled: true
        name: spring-ai-mcp-client
        type: SYNC
        request-timeout: 20s
        stdio:
          connections:
            filesystem:
              command: npx
              args:
                - "-y"
                - "@modelcontextprotocol/server-filesystem"
                - "D:/data/kb"
@Service
class DocService {

    private final ChatClient chatClient;
    private final List<ToolCallbackProvider> mcpProviders;

    DocService(ChatClient.Builder builder, List<ToolCallbackProvider> mcpProviders) {
        this.chatClient = builder.build();
        this.mcpProviders = mcpProviders;
    }

    String ask(String q) {
        return this.chatClient.prompt()
                .user(q)
                .tools(this.mcpProviders)
                .call()
                .content();
    }
}

启动时会拉起 npx 子进程、完成握手、发现工具；之后每次提问，工具定义会随请求发给模型， 模型决定调用时由客户端转发给子进程执行。

Windows 上 npx 直接写 command 会失败

npx 是 .cmd 脚本，不能直接 exec。改成 command: cmd，args: ["/c", "npx", "-y", "..."]。macOS / Linux 才能直接写 npx。

配置项：一个前缀管三类连接

配置项 默认值 说明
spring.ai.mcp.client.enabled true 总开关
...client.type SYNC SYNC / ASYNC，决定注入的客户端类型
...client.request-timeout 20s 单次工具调用超时
...client.initialized true 启动时是否立刻握手
...client.toolcallback.enabled true 是否把 MCP 工具暴露成 ToolCallbackProvider
...client.stdio.connections.<name> — command / args / env
...client.sse.connections.<name> — url + sse-endpoint
...client.streamable-http.connections.<name> — url + endpoint

公共配置McpClientCommonProperties.java:34； stdio 前缀McpStdioClientProperties.java:48； SSE 前缀McpSseClientProperties.java:65； Streamable HTTP 前缀McpStreamableHttpClientProperties.java:49。

    mcp:
      client:
        streamable-http:
          connections:
            knowledge:
              url: https://mcp.example.com
              endpoint: /mcp
        sse:
          connections:
            legacy-tools:
              url: http://localhost:3000

工具发现：名字、前缀与过滤

客户端握手后会拉取工具清单，每个工具变成一个 ToolCallback。多个 MCP server 之间如果出现同名工具， DefaultMcpToolNamePrefixGenerator 会给它们加前缀来区分。

但它只处理 MCP 内部的冲突：本地 @Tool 与远端 MCP 工具重名时，它不知道。 这类冲突会在合并后的列表经过 ChatClient 时被检测到，并抛 IllegalStateException。 

@Bean
McpToolFilter onlyReadOnlyTools() {
    return (connection, tool) -> !tool.name().startsWith("delete")
            && !tool.name().startsWith("write");
}

过滤接口是 BiPredicate<McpConnectionInfo, McpSchema.Tool>McpToolFilter.java:30； 命名冲突与过滤的官方说明tools.adoc:410。

重名冲突的后果取决于调用路径

经过 ChatClient：合并列表时校验，重名直接失败，不会执行错工具。绕过 ChatClient 直接调 ChatModel：按名字解析，先出现的赢，没有报错也没有日志——远端工具可能 冒名执行。混合本地与 MCP 工具时，务必让名字天然不冲突。

生命周期：握手、超时与关闭

  • ① 启动时创建客户端
    自动装配为每个连接建一个 McpSyncClient（或 Async），并按 initialized=true 执行握手。 McpClientAutoConfiguration.java:190
  • ② 发现工具
    握手后拉取工具清单，构建 ToolCallbackProvider。
  • ③ 每次调用受 request-timeout 约束
    默认 20 秒。工具本身很慢时，调大这个值，而不是调大模型的超时。
  • ④ 关闭
    应用停止时客户端会被关闭，stdio 子进程随之退出；异常退出可能留下孤儿进程，容器部署要留意。

    • 安全边界：MCP server 不是「可信代码」

    MCP 只定义协议，不定义信任。一个 MCP server 能做什么，完全取决于它自己的实现和你的授权：

    风险 场景 缓解
    任意命令执行 stdio server 以你的用户权限运行 固定 command 与参数，不接受用户输入拼命令
    数据外泄 工具把文件内容发给远端 只接可信 server；用 McpToolFilter 限制工具
    权限过大 文件系统 server 挂载了整个磁盘 只挂载必要目录，用只读挂载
    远端服务伪造 SSE / HTTP 地址被替换 HTTPS + 鉴权头 + 固定域名
    不要把「模型能调用」等同于「可以放心调用」

    模型只负责提议，执行权在客户端。删库、转账、发消息这类工具，即使只是 MCP 暴露出来的，也要在服务端做 二次校验与幂等，不能依赖提示词里的「请谨慎」。

    速查表

    你要做的事 写法
    接入本地进程 spring.ai.mcp.client.stdio.connections.<name>.command/args/env
    接入远程 SSE ...sse.connections.<name>.url + sse-endpoint
    接入远程 HTTP ...streamable-http.connections.<name>.url + endpoint
    在对话里使用 .tools(mcpToolCallbackProvider)
    限制暴露的工具 定义一个 McpToolFilter Bean
    调大工具超时 spring.ai.mcp.client.request-timeout=60s
    异步客户端 spring.ai.mcp.client.type=ASYNC

    陷阱与窍门

    启动卡住或报握手失败

    因为子进程没起来（命令不存在、参数错、Windows 需要 cmd /c），或它把日志打到 stdout 污染了协议。改成先在终端手动执行同一条命令，确认能跑；server 日志一律走 stderr。

    工具在清单里，但模型从不调用

    因为没把 provider 挂到请求上，或者工具描述太差。改成确认 .tools(...) 生效，并用 McpToolFilter 先只留一两个工具，降低选择难度。

    本地工具突然「失灵」，实际调到了远端同名工具

    因为绕过了 ChatClient 的合并校验。改成统一走 ChatClient，或给 MCP 工具加前缀、给自己工具改名。

    工具执行 20 秒就超时

    因为request-timeout 默认 20s，与模型超时是两套。改成 按工具实际耗时调大，并让慢工具异步化（先返回任务 ID，再查询结果）。

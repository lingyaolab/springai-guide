13 · 可观测性与测试

AI 应用的故障很难复现：同一个问题，模型这次答对了，下次不一定。所以观测要能回答「这次慢在哪、 花了多少 token」，测试要能不依赖真实模型就把工具、RAG、Advisor 的逻辑锁住。这一章两件事一起讲。

读完你能做到

  • 说清一次请求会经过哪些 Observation，以及 token 用量从哪个对象取
  • 打开/关闭 prompt 与 completion 日志，并知道为什么默认关闭
  • 用 StubChatModel 和 StubEmbeddingModel 写出不花钱、可重复的单元测试
  • 直接测试 ToolCallback，不经过模型也能验证参数与异常

先说为什么：AI 应用不能只靠「看输出」

传统接口的 bug 可以靠断点复现；AI 应用的输出带随机性，问题往往藏在「检索错了」「工具没调」「token 超了」 这些中间环节。没有观测，你只能看到最终那句话；没有可替换的测试桩，你每跑一次测试都要花钱、还要等网络。

Observation：一次调用发生了什么
模型、Advisor、向量库、工具各自埋点，能拼出完整链路与耗时。
Metrics：趋势与成本
token 用量、调用次数、延迟分布，适合做告警与容量规划。
可替换的依赖：测试的基础
只要 ChatModel / EmbeddingModel 是接口，就能用桩替换。

Observation：哪些东西被埋了点

Spring AI 基于 Micrometer Observation。引入 spring-boot-starter-actuator 后，只要容器里有 ObservationRegistry，以下环节都会产生 observation：

环节 典型名称 / 上下文 能回答的问题
ChatClient gen_ai.client.operation 整次对话耗时、用了哪些 Advisor
Advisor 按 Advisor 分别记录 记忆、RAG、工具循环各花了多久
ChatModel 模型名、请求参数、token 用量、finish reason 是模型慢还是网络慢
EmbeddingModel 输入 token、维度 入库为什么慢、embedding 花了多少
VectorStore 查询向量、topK、返回条数 检索是不是空、命中几条
Tool Calling 工具名、参数、结果状态 模型到底调了哪个工具 
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>

接上 OpenTelemetry / Zipkin / Prometheus 之后，这些 observation 会变成 trace 与 metric。不做任何配置时， 它们也会被记录到 ObservationRegistry.NOOP——也就是什么都不留，所以「引了 starter 却没数据」 是正常的，要确认 registry 真的被装配了。

指标与 token：成本从哪里看

最有用的是 gen_ai.client.token.usage：它按输入/输出分别计数，可以按模型维度聚合。 Prometheus 里名字会变成 gen_ai_client_token_usage_total（点号被替换）。

指标 / 属性 含义
gen_ai.client.token.usage 输入与输出 token 数
gen_ai.usage.input_tokens 提示词 token
gen_ai.usage.output_tokens 生成 token
gen_ai.request.model 模型名，用来做维度切分
gen_ai.response.finish_reasons 停止原因（stop / length / tool_calls）

指标与属性清单observability/index.adoc:93。

高基数标签会把监控系统拖垮

不要把用户 ID、会话 ID、完整问题文本放进 metric 标签。它们适合放 trace 或日志。官方也明确区分： 低基数键进 metrics 与 traces，高基数键只进 traces。

代码里怎么拿 token 用量

ChatResponse response = chatClient.prompt()
        .user("解释一下 MVCC")
        .call()
        .chatResponse();

Usage usage = response.getMetadata().getUsage();
System.out.println(usage.getPromptTokens() + " + "
        + usage.getCompletionTokens() + " = " + usage.getTotalTokens());

Usage 是接口，DefaultUsage 是默认实现；getTotalTokens() 有默认方法， 两个分量缺失时按 0 计算。流式场景下，用量通常只在最后一个 chunk 或聚合后的响应里出现。

Usage 接口Usage.java:29； 元数据入口ChatResponseMetadata.java:89。

日志：默认不打印内容，是有意为之

配置项 默认 作用
spring.ai.chat.client.observations.log-prompt false 打印发送给模型的完整提示词
spring.ai.chat.client.observations.log-completion false 打印模型返回的完整内容
spring.ai.chat.observations.log-prompt false ChatModel 层的提示词日志
spring.ai.chat.observations.log-completion false ChatModel 层的返回内容日志

默认关闭是因为提示词里经常含用户隐私、密钥、内部文档。要排障时临时打开，并确保日志脱敏、有保留期限； 不要在生产长期打开。

日志开关与默认值observability/index.adoc:47。

单元测试：用 StubChatModel 替换真实模型

ChatModel 只强制实现 call(Prompt) 一个方法，stream 有默认实现（抛 UnsupportedOperationException）。所以写一个桩非常简单： 

class StubChatModel implements ChatModel {

    private final String reply;

    StubChatModel(String reply) {
        this.reply = reply;
    }

    @Override
    public ChatResponse call(Prompt prompt) {
        var generation = new Generation(new AssistantMessage(this.reply));
        return ChatResponse.builder()
                .generations(List.of(generation))
                .metadata(ChatResponseMetadata.builder()
                        .usage(new DefaultUsage(12, this.reply.length()))
                        .build())
                .build();
    }
}
@Test
void 返回模型文本并记录用量() {
    ChatClient chatClient = ChatClient.builder(new StubChatModel("你好，我是桩"))
            .build();

    ChatResponse response = chatClient.prompt()
            .user("打个招呼")
            .call()
            .chatResponse();

    assertThat(response.getResult().getOutput().getText()).isEqualTo("你好，我是桩");
    assertThat(response.getMetadata().getUsage().getPromptTokens()).isEqualTo(12);
}
需要按输入返回不同结果时

在桩里读取 prompt.getUserMessage().getText() 做分支，或者用 Mockito 的 when(chatModel.call(any()))。Spring 上下文里替换 Bean 用 @MockitoBean（Boot 4 已取代旧的 @MockBean）。

工具测试：绕过模型，直接调 ToolCallback

工具的执行不依赖模型。拿到 ToolCallback 之后，直接传 JSON 参数即可验证参数绑定、返回值与异常： 

@Test
void 工具能按城市返回结果() {
    ToolCallback[] callbacks = MethodToolCallbackProvider.builder()
            .toolObjects(new WeatherTools())
            .build()
            .getToolCallbacks();

    String result = callbacks[0].call("{\"city\":\"杭州\"}");

    assertThat(result).contains("杭州");
}

这样做的好处是：参数名、必填校验、异常转换逻辑都能被覆盖，而且不需要 API Key、没有网络抖动。 工具的调用上限与循环属于 Advisor 层，用上一章的 ToolCallingAdvisor 配置做集成测试即可。

从注解到 ToolCallback 的构建MethodToolCallbackProvider.java:86。

RAG 测试：用确定性向量验证「检索对不对」

测试 RAG 不需要真的 embedding 模型。写一个按关键词返回固定向量的桩，就能稳定验证排序与过滤： 

class StubEmbeddingModel implements EmbeddingModel {

    @Override
    public EmbeddingResponse call(EmbeddingRequest request) {
        throw new UnsupportedOperationException();
    }

    @Override
    public float[] embed(Document document) {
        return embed(document.getText());
    }

    @Override
    public float[] embed(String text) {
        // 两个维度足够演示：退款相关 / 运费相关
        return new float[]{
                text != null && text.contains("退款") ? 1f : 0f,
                text != null && text.contains("运费") ? 1f : 0f
        };
    }

    @Override
    public int dimensions() {
        return 2;
    }
}
VectorStore store = SimpleVectorStore.builder(new StubEmbeddingModel()).build();
store.add(List.of(
        new Document("refund", "退款政策：7 天无理由"),
        new Document("shipping", "运费规则：满 99 包邮")));

List<Document> hits = store.similaritySearch(
        SearchRequest.builder().query("退款怎么处理").topK(1).build());

assertThat(hits).hasSize(1);
assertThat(hits.get(0).getId()).isEqualTo("refund");
这测的是什么、不测什么

它验证的是你的代码：切分、过滤、topK、排序、拼接逻辑。它不验证真实 embedding 模型的语义能力—— 那属于评测（evaluation），要用真实模型和标注集跑。

集成测试：真实模型只在需要时跑

端到端测试仍然需要真实模型（或一个 Mock Server）。用环境变量守卫，避免 CI 没有 key 时红： 

@SpringBootTest
@EnabledIfEnvironmentVariable(named = "DEEPSEEK_API_KEY", matches = ".+")
class DeepSeekIT {

    @Autowired
    ChatClient chatClient;

    @Test
    void 能拿到真实回答() {
        String answer = chatClient.prompt().user("用一句话介绍杭州").call().content();
        assertThat(answer).isNotBlank();
    }
}

数据库/向量库这类依赖，用 Testcontainers 起真实实例，比 H2 模拟更可靠；pgvector 有现成镜像， 测试里把 initialize-schema 设为 true 即可。

陷阱与窍门

加了 actuator 还是看不到 token 指标

因为没有真正的 ObservationRegistry（比如手动 new 了 ChatModel），或者没接 Prometheus/OTel 导出。改成用自动装配的 ChatModel，并确认 registry 注入到了模型里。

测试里 mock 了 ChatClient，结果什么逻辑都没测到

因为把被测对象本身 mock 了。改成mock 最底层的 ChatModel / EmbeddingModel，让 Advisor、模板、解析这些真实逻辑跑起来。

流式测试拿不到 usage

因为用量通常在最后一个 chunk 或聚合响应里。改成测试里聚合整条流，或直接 用同步 call() 验证用量逻辑。

给桩加「可断言」的痕迹

在 Stub 里记录收到的 Prompt、调用次数、工具上下文，测试时断言「模型收到的提示词里确实拼进了检索结果」。 这比只断言最终字符串更能定位问题。

自检三问

  1. 为什么 prompt/completion 日志默认关闭？打开后要注意什么？
  2. 测试工具时为什么可以完全不经过模型？
  3. 用 StubEmbeddingModel 测 RAG，能验证什么、不能验证什么？

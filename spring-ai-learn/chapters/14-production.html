把 demo 放上线，最先出事的往往不是模型答得不好，而是一次超时被重试放大成十次、 429 被当成不可重试直接失败、流式连接挂了一小时。 这一章用源码里的默认值解释这些现象，并给出可落地的配置。

先说为什么：AI 调用的失败模式与普通 HTTP 不同

普通接口失败通常是「挂了」，重试一次就好。模型调用失败有更多形态：限流（429）、超时（生成到一半）、 内容审核拒绝、上下文超长、余额不足。把它们混在一起无脑重试，轻则延迟爆炸，重则账单翻倍。

可重试：网络抖动、5xx、连接重置
重试有意义，但要限次数、限总时长。
不该重试：401、403、404、上下文超长、内容审核
重试一百次结果一样，只会浪费钱。
要特殊处理：429 限流
应该退避 + 排队，而不是立刻放弃，也不是立刻重试。

重试：默认值有多激进

参数 默认值 问题
最大重试次数 10 配置项叫 max-attempts，源码却传给 maxRetries：加首次一共最多 11 次请求
初始间隔 2 秒 对在线接口来说太长
退避倍数 5 2s → 10s → 50s → 180s
最大间隔 3 分钟 最坏总等待超过 20 分钟（约 22 分钟）

默认常量RetryUtils.java:50； 配置属性SpringAiRetryProperties.java:39。

哪些异常会被重试

默认模板只重试 TransientAiException 与 ResourceAccessException（网络层）； 4xx 会被错误处理器归类为 NonTransientAiException，直接抛出。这个分类发生在响应错误处理器里， 不是模型层。RetryUtils.java:111

max-attempts 其实是「重试次数」

SpringAiRetryAutoConfiguration 把它传给 RetryPolicy.maxRetries(...)， 所以设 3 是「重试 3 次、总共最多 4 次请求」，不是「总共 3 次」。 SpringAiRetryAutoConfiguration.java:66

429 默认不重试，这是个常见的「反直觉」

429 属于 4xx，因此默认被归为不可重试。高并发下你会看到大量「限流就失败」而不是「等一等再试」。 正确做法：要么 on-http-codes: [429]，要么在业务层用令牌桶/队列自己控制速率， 并把重试预算留给上游抖动。

超时：三层，别只设一个

层 典型值 设置位置 失败表现
连接超时 3–5s RestClient / WebClient 的 request factory 连不上，快速失败，可重试
读超时（首字节） 30–60s HTTP 客户端 模型排队或生成慢，超时
流式总时长 60–120s Flux.timeout(...) 连接建立后一直有数据但总也结束不了 
@Bean
RestClientCustomizer restClientTimeout() {
    return builder -> {
        var factory = new SimpleClientHttpRequestFactory();
        factory.setConnectTimeout(5_000);    // 毫秒
        factory.setReadTimeout(60_000);
        builder.requestFactory(factory);
    };
}

Spring AI 的模型自动装配使用容器里的 RestClient.Builder / WebClient.Builder， 所以通过 Boot 的 customizer 定制一次，对所有厂商生效。流式则一定在 Flux 上再加一层总超时， 因为「读超时」管不到一个持续有数据、但永不结束的连接。

超时不是越小越好

推理模型的思考阶段可能长时间没有输出。把首字节超时设成 5 秒，会把正常请求全部杀掉。 按 P99 设定，并给流式留更长的总时长。

限流：应用层不控制，厂商会替你控制

Spring AI 没有内置限流器。可选三处：网关（最外层）、应用（按用户/租户）、厂商（TPM/RPM）。 常见组合是「网关做粗粒度 + 应用做令牌桶 + 监控 429 比例」。 

@Bean
RateLimiter tenantLimiter() {
    var config = RateLimiterConfig.custom()
            .limitForPeriod(20)                       // 每秒 20 次
            .limitRefreshPeriod(Duration.ofSeconds(1))
            .timeoutDuration(Duration.ZERO)           // 拿不到就快速失败
            .build();
    return RateLimiter.of("llm", config);
}

限流之外还要限制并发：几十个流式请求同时挂着会占满连接池和 boundedElastic 线程。用信号量或 WebFlux 的并发控制，别让慢请求把整个服务拖住。

把「等待」变成产品体验

被限流时返回「当前排队第 N 位」或「预计 10 秒」，比直接 500 好得多。流式接口可以先发一个 event: queue，再发正文。

降级：主模型挂了怎么办

Spring AI 通过 spring.ai.model.chat 选择模型，但那是启动期决策。运行期降级需要自己包一层： 

class FallbackChatModel implements ChatModel {

    private final List<ChatModel> delegates;

    FallbackChatModel(ChatModel primary, ChatModel secondary) {
        this.delegates = List.of(primary, secondary);
    }

    @Override
    public ChatResponse call(Prompt prompt) {
        RuntimeException last = null;
        for (ChatModel model : this.delegates) {
            try {
                return model.call(prompt);
            }
            catch (RuntimeException ex) {
                last = ex;   // 记录并尝试下一个
            }
        }
        throw Objects.requireNonNull(last);
    }

    @Override
    public ChatOptions getOptions() {
        return this.delegates.get(0).getOptions();
    }

    @Override
    public Flux<ChatResponse> stream(Prompt prompt) {
        // 流式降级只适合「首个 chunk 之前」失败；中途失败应补一句兜底文本
        return this.delegates.get(0).stream(prompt);
    }
}
降级不是免费的

第二个模型的输出风格、结构化输出能力、上下文长度都可能不同。降级前要确认：提示词是否通用、 工具 schema 是否兼容、计费是否可接受。最稳的降级是「返回缓存/固定话术」，而不是换一个你没测过的模型。

成本：先算清楚，再谈优化

Usage usage = response.getMetadata().getUsage();

BigDecimal inputPrice = new BigDecimal("0.0000005");   // 每 token 单价，按厂商价目表填
BigDecimal outputPrice = new BigDecimal("0.000002");

BigDecimal cost = inputPrice.multiply(BigDecimal.valueOf(usage.getPromptTokens()))
        .add(outputPrice.multiply(BigDecimal.valueOf(usage.getCompletionTokens())));

优化顺序（从收益最大、风险最低开始）：

  1. 减少输入 token：把 RAG 的 topK 从 10 降到 3–4，去掉重复上下文。
  2. 减少调用次数：不要每轮都改写查询；缓存相同问题（包括语义缓存）。
  3. 分级模型：分类、改写用小模型，最终回答用大模型。
  4. 控制输出：设 maxTokens，要求结构化/简短输出。
  5. 压缩历史：窗口裁剪 + 摘要，而不是把全部历史每轮重发。

用量的字段来源Usage.java:29； 指标口径见第 13 章。

陷阱与窍门

一次故障后账单翻倍

因为默认重试 10 次、退避 5 倍。改成在线服务把重试次数降到 2–3、 退避改成 2 倍，并设置总超时。

限流时大量请求直接失败

因为429 是 4xx，默认不重试。改成on-http-codes: [429]， 或在入口做令牌桶，避免打到厂商限流。

流式接口连接挂很久不释放

因为只设了读超时，没设流式总时长。改成 Flux.timeout(...) + 客户端断开时取消，并检查代理的空闲超时。

降级到备用模型后，结构化输出解析失败

因为备用模型不支持原生 structured output，或提示词不适配。改成 降级时同时降级输出要求（返回纯文本），或只对「非关键路径」启用备用模型。

15 · 综合案例

把前 14 章拼成一个真实服务：企业知识库问答。要求是：能查内部文档、能调订单工具、 支持多轮、流式返回、答案带引用、失败能降级、成本可观测。这一章给完整骨架与每个决策的理由。

读完你能做到

  • 画出「文档入库」与「在线问答」两条链路的组件与数据流
  • 把 ChatClient、Advisor、工具、向量库、记忆组装成一个可运行工程
  • 实现带引用的流式回答，并处理取消、超时与降级
  • 用一份配置和一个 compose 文件把服务跑起来

架构：两条链路，五个组件

离线：文档入库
文档源 → Reader → TokenTextSplitter → EmbeddingModel → VectorStore（pgvector）。 用文档哈希做幂等，重复导入不产生重复块。
在线：一次提问
用户问题 → 记忆 Advisor（取历史）→ RAG Advisor（改写/检索/拼上下文）→ 工具 Advisor（按需调订单） → ChatModel（DeepSeek）→ 流式返回 + 引用。
横切：观测、限流、降级
Observation 记录链路，Retry/超时兜底，失败时返回缓存或固定话术。

为什么这样切：入库与问答的负载特征完全不同——入库是批量、可重试、离线；问答是在线、低延迟、要限流。 分开之后，两边可以独立扩容与调参。

入库：幂等、可重跑

@Service
class IngestService {

    private final VectorStore vectorStore;

    IngestService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    int ingest(String sourceName, String text) {
        // 用内容哈希做文档 id：同一份文档重复导入时覆盖而不是追加
        String id = DigestUtils.md5DigestAsHex(text.getBytes(StandardCharsets.UTF_8));

        Document document = Document.builder()
                .id(id)
                .text(text)
                .metadata(Map.of(
                        "source", sourceName,
                        "embedding_model", "all-MiniLM-L6-v2",
                        "version", 1))
                .build();

        var chunks = TokenTextSplitter.builder().build().apply(List.of(document));
        this.vectorStore.add(chunks);
        return chunks.size();
    }
}

三个细节：① id 由内容决定，重跑不会产生重复；② metadata 记录来源与 embedding 模型，方便引用与迁移； ③ 切分放在入库时做，查询时只负责检索。

问答：一条 Advisor 链

@Configuration
class ChatConfig {

    @Bean
    ChatClient chatClient(ChatClient.Builder builder,
                          ChatMemory chatMemory,
                          VectorStore vectorStore) {

        var memory = MessageChatMemoryAdvisor.builder(chatMemory).build();

        var rag = QuestionAnswerAdvisor.builder(vectorStore)
                .searchRequest(SearchRequest.builder()
                        .topK(4)
                        .similarityThreshold(0.55)
                        .build())
                .build();

        return builder
                .defaultSystem("""
                        你是企业知识库助手。
                        只根据提供的上下文回答；上下文没有的信息，明确说「资料中没有」。
                        回答控制在 200 字以内，并在末尾列出引用的来源文件名。
                        """)
                .defaultAdvisors(memory, rag)
                .defaultTools(new OrderTools())
                .build();
    }
}
order 提醒

记忆在 MIN+200、工具在 MIN+300、RAG 在 0。所以一次带工具的问答里， RAG 会在工具循环的每一轮重新检索。若不想这样，把 RAG 的 order 调到小于 MIN+300。

工具：业务上下文不要交给模型填

@Component
class OrderTools {

    private final OrderRepository orders;

    OrderTools(OrderRepository orders) {
        this.orders = orders;
    }

    @Tool(description = "按订单号查询当前用户的订单状态，只读")
    OrderView queryOrder(
            @ToolParam(description = "订单号，例如 SO-20261106-001") String orderNo,
            ToolContext context) {

        String userId = (String) context.getContext().get("userId");
        return this.orders.findByUserAndOrderNo(userId, orderNo);
    }
}

流式与引用

@RestController
class ChatController {

    private final ChatClient chatClient;

    ChatController(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    // MVC 栈：用 SseEmitter 桥接；如果项目是 WebFlux，直接返回 Flux<ServerSentEvent<String>> 即可
    @PostMapping("/chat/stream")
    SseEmitter stream(@RequestBody ChatRequest request) {
        SseEmitter emitter = new SseEmitter(0L);

        Disposable d = this.chatClient.prompt()
                .user(request.question())
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, request.conversationId()))
                .toolContext(Map.of("userId", request.userId()))
                .stream()
                .content()
                .timeout(Duration.ofSeconds(90))
                .subscribe(
                        chunk -> send(emitter, "delta", chunk),
                        error -> {
                            send(emitter, "error", "生成中断，请稍后重试");
                            emitter.complete();
                        },
                        () -> {
                            send(emitter, "done", "[DONE]");
                            emitter.complete();
                        });

        emitter.onCompletion(d::dispose);
        emitter.onTimeout(d::dispose);
        return emitter;
    }

    private static void send(SseEmitter emitter, String event, String data) {
        try {
            emitter.send(SseEmitter.event().name(event).data(data));
        }
        catch (IOException e) {
            emitter.completeWithError(e);
        }
    }
}

引用信息在 QuestionAnswerAdvisor 的检索结果里。要在流开始前拿到它，可以先用同一条 RAG 链做一次 「预检索」，或把 QuestionAnswerAdvisor 换成 RetrievalAugmentationAdvisor， 从 rag_document_context 取文档，作为第一个 SSE 事件发出。

RAG 上下文 keyRetrievalAugmentationAdvisor.java:64； 记忆会话参数ChatMemory.java:36。

陷阱与窍门

上线后回答质量比 demo 差很多

因为demo 只测了十几个问题，真实问题措辞千奇百怪。改成先建回归集， 再调 topK/阈值/改写，不要凭感觉改提示词。

多轮对话里引用错乱

因为RAG 在工具循环内重复检索，或历史里混入了上一轮的上下文。改成 每轮回答只展示本轮检索到的文档 id，并把引用与消息一起持久化。

同一份文档被重复入库

因为每次导入都生成新 id。改成用内容哈希或业务主键做 Document id，并在入库前先删旧版本。

成本失控

因为topK 太大、历史全量重发、每轮都改写查询。改成按第 14 章的顺序优化， 并用 token 指标做预算告警。

16 · 评测

改了 prompt、换了模型、调了 topK 之后，怎么知道是变好还是变差？靠「感觉答得不错」不行。 这一章给三层可落地的评测：确定性断言、离线回归集、在线指标， 并讲清内置 Evaluator 与 LLM-as-judge 的真实边界。

读完你能做到

  • 把「回答质量」拆成可测量的检索指标与生成指标，而不是一个笼统的分数
  • 用 50 条左右的回归集，在 CI 里挡住「改坏了」的提交
  • 用内置 RelevancyEvaluator / FactCheckingEvaluator 做生成质量判断
  • 说清 LLM-as-judge 的三种偏差，以及为什么 judge 不能和被测模型同源

先说为什么：没有基线的优化都是猜测

调 RAG 最常见的循环是：改 topK → 问两个问题 → 感觉好多了 → 上线 → 用户说更差了。 问题在于你比较的是「两个记忆中的样本」，不是同一批固定输入。评测要做的，就是把这批输入固定下来， 让每次改动都有同一把尺子。

确定性断言（第 13 章）
工具参数、JSON 解析、模板拼接。答案唯一，适合单元测试。
离线回归集（本章重点）
固定问题 + 期望证据 + 期望事实，跑检索指标与生成判断。
在线指标
点赞/点踩、引用点击、转人工率、延迟与 token 成本。
三层解决的是不同问题

离线回答「这次改动有没有变差」；在线回答「真实用户是否满意」；确定性断言回答「代码逻辑有没有写错」。 三层都不能互相替代，尤其不能拿在线点赞数去调 topK——噪音太大、周期太长。

先分清：检索指标 vs 生成指标

指标 衡量什么 需要 LLM 吗 稳定性
recall@k 相关文档有没有被召回 不需要 高
MRR 第一个相关结果排得多靠前 不需要 高
hit rate 多少问题至少命中一条 不需要 高
Relevancy 回答是否与上下文一致 需要（judge） 中
Fact checking 回答是否被文档支持 需要（judge） 中
人工评分 整体有用性 需要人 高但贵

顺序很重要：先保证检索能召回，再谈回答好不好。检索错了，生成指标再高也只是「基于错误上下文的自洽」。

回归集：50 条就够，但要选对

一份可用的回归集至少包含四类样本，别只收集「正常问题」：

类型 例子 防什么
常规问题 「满多少包邮？」 基础召回
同义改写 「运费怎么免？」 只会匹配原词的检索
多轮追问 「那退款呢？」（上文在聊运费） 不改写就直接检索
不该回答 「帮我写一首诗」 没有依据也硬编

{"id":"ship-02","question":"运费怎么免？","relevantIds":["doc-shipping#0"],"mustInclude":["99"]}

chunk id 与源文档 id 不是一回事

切分之后，每个 chunk 的 id 由切分器重新生成。回归集如果只标「源文件名」，你无法判断命中的是第几块； 如果标了旧 id，重建索引后又对不上。可靠做法：入库时把 source + chunkIndex 写进 metadata，回归集按这两个字段断言。

检索指标：三个公式，一段代码

设第 i 个问题的相关文档集合为 Rᵢ，检索返回前 k 条为 Tᵢ(k)：

指标 公式 直觉
recall@k |Rᵢ ∩ Tᵢ(k)| / |Rᵢ| 该找到的找到了多少
MRR mean(1 / rank(first relevant)) 第一条相关结果排第几
hit rate@k count(hit) / N 多少问题至少命中一条 
record Case(String question, Set<String> relevantIds) {}
record Report(double recallAtK, double mrr, double hitRate, double refusalRate) {}

Report evaluate(VectorStore store, List<Case> cases, int k) {
    double recall = 0;
    double mrr = 0;
    int hits = 0;
    int positives = 0;
    int negatives = 0;
    int refusals = 0;

    for (Case c : cases) {
        List<String> ids = store.similaritySearch(
                        SearchRequest.builder().query(c.question()).topK(k).build())
                .stream().map(Document::getId).toList();

        // 「不该回答」的样本单独统计，不混进 recall / MRR 分母
        if (c.relevantIds().isEmpty()) {
            negatives++;
            if (ids.isEmpty()) {
                refusals++;
            }
            continue;
        }

        positives++;
        long found = ids.stream().filter(c.relevantIds()::contains).count();
        recall += found / (double) c.relevantIds().size();

        int first = java.util.stream.IntStream.range(0, ids.size())
                .filter(i -> c.relevantIds().contains(ids.get(i)))
                .findFirst().orElse(-1);
        if (first >= 0) {
            hits++;
            mrr += 1.0 / (first + 1);
        }
    }

    int n = positives;
    int denominator = n == 0 ? 1 : n;
    double refusalRate = negatives == 0 ? 0 : refusals / (double) negatives;
    return new Report(recall / denominator, mrr / denominator, hits / (double) denominator, refusalRate);
}

对「不该回答」的样本（relevantIds 为空），只有一条文档都没召回才算通过；这类样本单独统计 refusalRate，不要混进 recall / MRR 的分母，否则指标会互相污染。

先跑一次基线，再谈阈值

新项目没有基线时，先记录当前值（比如 recall@4 = 0.62），然后把「不允许低于基线 5%」作为门禁。 直接照搬别人的 0.9 只会让你永远发不了版。

它们只认「yes」，而且只给 0/1

两个内置实现都是把 judge 的回答 strip() 后与 "yes" 做忽略大小写比较， 其它任何内容都算失败。模型回 Yes.（带句号）或 The answer is yes 都会被判否。 自定义 prompt 时必须强制「只输出 yes 或 no」，否则通过率会莫名其妙地低。 RelevancyEvaluator.java:84

LLM-as-judge：三种偏差，绕不开

用模型当裁判是可行的：评判比生成简单，研究上它与人类判断的一致率可以接近人类之间的一致率。 但它是有偏的测量工具，不校准就会得出错误结论。

偏差 表现 缓解
自恋偏差 judge 偏爱自己生成的答案 用不同厂商/不同模型做 judge；至少不同参数
位置偏差 pairwise 时偏爱第一个或第二个 A/B 交换顺序各评一次，只统计一致的胜负
长度/格式偏差 更长、更有条理的回答得分更高 控制长度、盲评、把评分维度拆开

两种模式：point-wise（单条回答打 1–4 分，适合做通过率）与 pairwise（两条回答二选一，适合 A/B）。前者便宜，后者更接近人类偏好但要做位置交换。

两种模式与 judge 选型llm-as-judge.adoc:23； 官方示例明确要求「用独立的 ChatClient 避免自恋偏差」llm-as-judge.adoc:175。

自纠正：把 judge 接回 Advisor 链

评测不只能离线跑。官方 guide 给了一个「生成 → 评判 → 带反馈重试」的递归 Advisor： judge 打分不达标时，把反馈追加到请求里重新生成，直到达标或用完重试次数。 

public ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain) {
    ChatClientResponse response = chain.nextCall(request);

    for (int attempt = 1; attempt <= maxRepeatAttempts + 1; attempt++) {
        Evaluation evaluation = judge(request, response);   // 独立 judge 模型

        if (evaluation.rating() >= successRating) {
            return response;
        }
        if (attempt > maxRepeatAttempts) {
            logger.warn("评分未达标，返回最后一次响应：{}", evaluation.feedback());
            return response;
        }

        // 把反馈拼回请求，重新走一遍后面的链
        ChatClientRequest retry = addFeedback(request, evaluation.feedback());
        response = chain.copy(this).nextCall(retry);
    }
    return response;
}

它复用了第 06 章的 chain.copy(this) 递归机制，和第 10 章的工具循环是同一个套路。 代价也很直接：一次回答最多变成 1 + maxRepeatAttempts 次生成 + 同样次数的 judge 调用。

别把它放进主链路

自纠正适合「质量优先、可接受延迟」的场景（报告生成、代码修复），不适合聊天首响。 真要上线，至少设上限、超时、并在 judge 失败时降级返回原始回答。

CI 门禁：让「改坏了」发不出去

把评测做成一个普通的 JUnit 测试，用环境变量守卫真实模型调用，用阈值做断言：

@EnabledIfEnvironmentVariable(named = "RUN_EVAL", matches = "true")
class RegressionEvalTest {

    @Test
    void 检索指标不得低于基线() {
        Report report = new RetrievalEval().evaluate(vectorStore, GoldenSet.load(), 4);

        assertThat(report.recallAtK()).isGreaterThanOrEqualTo(0.62);
        assertThat(report.hitRate()).isGreaterThanOrEqualTo(0.85);
        assertThat(report.mrr()).isGreaterThanOrEqualTo(0.55);
    }

    @Test
    void 生成相关性通过率不得低于基线() {
        long passed = GoldenSet.load().stream()
                .filter(c -> !c.relevantIds().isEmpty())
                .filter(c -> evaluator.evaluate(toRequest(c)).isPass())
                .count();

        assertThat(passed / (double) GoldenSet.load().size()).isGreaterThanOrEqualTo(0.80);
    }
}
实践 原因
只在 PR / nightly 跑 每次提交都调真实模型太贵
固定随机种子/温度 0 减少非确定性带来的假失败
同一输入跑 3 次取多数 单次结果参考价值低
失败样例落盘 只看通过率无法定位问题
阈值相对基线 绝对分数没有可比性

成本：评测本身也是一笔开销

一次生成评估 = 1 次被测模型调用 + 1 次 judge 调用；50 条 × 3 次重复 × 2 次调用 = 300 次调用。 用大模型当 judge，很容易比线上流量还贵。三个控制手段：

  1. 缓存：以「问题 + 回答 + judge prompt + judge 模型」的哈希做 key，命中直接复用。
  2. 分层：检索指标零成本，每次都跑；生成指标只在改动 prompt/模型时跑。
  3. 小模型 judge：先用小模型筛明显失败，再用大模型复核边界样本。
人工校准 50 条，换长期自动化

judge 的分数只有和人工判断对齐才有意义。抽 50 条人工打分，比较 judge 与人的一致率； 一致率低就先改 prompt/换 judge，而不是直接信分数。

陷阱与窍门

用检索到的同一段上下文做 judge，等于自己证明自己

因为Relevancy 只判断「回答是否与给定上下文一致」，不判断上下文本身是否正确。 改成再配一层 Fact checking + 人工抽检，或对关键事实做规则断言（必须包含某数字/日期）。

通过率突然掉到 20%

因为judge 回了 Yes. 而代码只认 yes。改成 在自定义 prompt 里强制「只输出小写 yes 或 no」，或在评估器外面包一层容错解析。

同一版本跑两次，指标差很多

因为温度、并发、judge 的非确定性。改成温度设 0、固定回归集顺序、 重复 3 次取多数，并记录每次的原始输出。

回归集全是「好回答」

因为只收集了成功案例。改成按「常规 / 改写 / 多轮 / 不该回答」四类配比， 并定期把线上失败案例补进去。
